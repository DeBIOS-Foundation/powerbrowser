**As a** Power Browser user, **I want to** be told once that the interface cannot start and be left
alone, and **I want to** know that quitting the browser really stops everything it started, **so
that** a broken install does not spawn a process every fifteen seconds and a quit does not leave a
Node backend running behind my back.

Close 01-VERIFICATION.md's failed truths 2d (CR-02) and 2e (CR-03). They are one plan because they
are one interaction: `_showError` calls `_startRecoveryProbe()` unconditionally, never inspecting the
`recoverable` flag it was just handed, and `PowerBrowserAPI.onQuitGranted` is registered at line 181
— after the settings-folder `ensureDirectory` try/catch that can return at line 167. That catch
classifies its failure `recoverable: true`, so the ungated probe still runs on that path and can
drive a spawn all the way through the health gate to a swap: a live, healthy, supervised backend on a
launch that never registered a quit observer and never derived `_stateFilePath`. Fixing the probe gate
narrows the second defect but does not close it — the settings-folder path is legitimately
recoverable, so its probe still runs after the gate lands, and the ordering is the only thing that
makes that safe.

half of SEC-01 — a leaked backend past quit is still authenticated by the token it was handed at
spawn, so the fail-closed gate does not help once the process has outlived its supervisor.

behavioural scenarios on the analyzer plan 01-11 created, one tree-derived ordering rule, and one

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| supervised backend process ↔ browser lifetime | The backend is a Node process with the Theia extension host's filesystem access and terminal surface, holding the per-launch token it was handed on stdin. Whether it dies with the browser is decided entirely by whether `onQuitGranted` was registered on the launch that spawned it. |
| failure classification (`recoverable`) → retry machinery | An untrusted-in-effect input to the probe: a wrong classification, or an ignored one, turns a one-shot failure into an unbounded loop. |
| crash-leftover state file → next launch's `_reapLeftover()` | A launch that spawned without deriving `_stateFilePath` leaves nothing for the next launch to verify and reap, so an orphan survives indefinitely. |

## STRIDE Threat Register (ASVS L1, block on `high`)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-12-01 | Denial of Service | `_showError` → `_startRecoveryProbe()` | high | mitigate | An unrecoverable resolve failure starts an unbounded respawn loop — one spawn attempt every `recoveryProbeIntervalMs` (15 s default) for the life of the session, against `_configDir` and `_stateFilePath` that were never assigned. Each attempt is a process spawn, so the cost is real, not notional. Task 1 gates the probe on the classification the method already receives, with a positive control proving the recoverable side still probes. |
| T-01-12-02 | Elevation of Privilege | supervised backend lifetime vs `onQuitGranted` registration order | high | mitigate | A backend spawned via the probe on a launch that returned at the settings-folder branch is healthy, swapped, and unobserved: `stop()` never runs on quit, so a Node process with the extension host's file access and an open terminal surface outlives the browser, still authenticated by the token it was handed at spawn. SEC-01's fail-closed gate cannot revoke it — the process already passed the gate. Task 2 registers the observer and derives the state-file path before every branch that can reach a spawn. |
| T-01-12-03 | Repudiation | crash-leftover record for `_reapLeftover()` | high | mitigate | The same launch derives no `_stateFilePath`, so a crash leaves no verified-identity record and the next launch's reap finds nothing.
