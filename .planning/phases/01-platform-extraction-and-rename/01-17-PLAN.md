01-15 correctly closed CR-B by giving the scan a real `--extra-root` filesystem walk, proven live over
a 463,930-file checkout. The new mode has two holes of its own, both reproduced against the shipped
script by the reviewer and re-reproduced independently by the verifier:

**CR-01** — the extra-root `scan()` call passes no `rows` filter, so it reuses the full inventory
including the three `coincidental` rows. In `claimOccurrences`, longest-token-first ordering lets the
28-character row holding this checkout's own absolute source path win over the shorter
`brand-identifier` row inside it. The whole span is marked in `taken[]`, the occurrence is classified
`coincidental` and therefore is not an offence, AND the independent residue probe at that index is
suppressed. In the tracked-tree pass that is safe only because `reconcile()` condition 2 asserts the
row's observed count is zero; the extra-root pass deliberately does not run `reconcile()`, for a
stated and correct reason, so nothing constrains it there at all. The net effect is that the single
most likely residue in a replayed tree — an absolute source or objdir path baked into a mozconfig, a
patch header, or a generated build file — passes the gate whose entire purpose is catching it.

**CR-02** — `scan()`'s per-file read is wrapped in a silent `catch { continue; }` whose comment
justifies it as "a path git tracks but this checkout does not materialise". That holds for the
`git ls-files` source only. Every path in the extra-root set came from a `readdirSync` that just
reported it as an existing regular file, so a throw there means EACCES, EISDIR, or a read past the V8
string limit — never "not materialised". The file is skipped, no failure is recorded, and it is still
counted in the reported file total, so the operator is told a file was scanned that was never opened.

**Scope fence.** This does not change the tracked-tree scan's file set, its row set, its verdict or
its reconciliation arithmetic — all of which `--quick` re-confirmed green this pass. The gap is scoped
to the extra-root pass's row set and to the shared per-file catch's two provenances.

Purpose: `rebase-upstream.sh`'s own comment gives the reason the gate runs at that call site — a
rebase is the one routine operation that pulls in content nobody in this repo wrote. Both holes are
the same failure class CR-B itself was, which is the same class CR-A and CR-03 were: a gate placed at
exactly the right call site whose own mechanics keep it green by construction on the specific input it
exists to catch. This is the third consecutive pass to find that class, each time in the code the
previous pass shipped.
