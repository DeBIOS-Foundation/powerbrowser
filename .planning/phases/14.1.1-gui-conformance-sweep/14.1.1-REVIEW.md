self-tests pass on this tree (`shell-gbrowser-standin`, `backend-env-readers`,
`gui09-setups-copy`), `scan-brand-residue`, `check-internals-boundary` and

`theia/node_modules/@theia/core/lib/browser/shell/shell-layout-restorer.js:377-383` —

## Critical Issues

### CR-01: The thumbnail phase cannot fail if the G-14.1.1-6 last-view capture site is deleted

**File:** `scripts/verify-web-tab-live.mjs:751-772` (phase), `:1237-1246` (assertions);
`powerbrowser/shell/PowerBrowserAPI.sys.mjs:2355-2364` (the site under test)

**Issue:** The `thumbnail` phase hides the overlay through a `visible:false` geometry
message and then polls `P.thumbnailOf(cfg.servedB)` for *any* non-empty string:

```js
await P.until(async () => {
    snapshot = await P.thumbnailOf(cfg.servedB);
    return typeof snapshot === 'string' && snapshot.length > 0;
}, 8000);
```

There is no baseline read and no clear-before-hide. By the time this phase runs, a
snapshot for `servedB` has **already** been written by the *other* schedule site added
in the same plan — the network-STOP arm at `PowerBrowserAPI.sys.mjs:2262`, which fired
when the lost-view reopen reloaded `servedB` several phases earlier and settled 500 ms
later (`TAB_THUMBNAIL_SETTLE_MS`). The `P.until` predicate is therefore satisfied on
its first poll, before the hide has had any effect. Deleting the entire hide-time
capture block at `:2355-2364` leaves all three thumbnail assertions green.

The file documents a *different* limitation honestly (the `thumb-not-scheduled` plant
strips the read, not the schedule, `:548-566`) and that note is correct — but it does
not cover this one, and the check's own header claims the phase exercises "the
last-view schedule site". It does not.

**Fix:** Take a baseline before the hide and require a *change*, so the assertion is
about the hide-time site rather than about any snapshot ever existing:

```js
// before the hide
report.thumbnail.before = await P.thumbnailOf(cfg.servedB);
await P.thumbnailOf.clear?.(cfg.servedB);   // or navigate to a third served URL
                                            // whose only capture opportunity is the hide
P.channel.send({ kind: 'webTabGeometry', tabId: P.widget.tabId, x: 0, y: 0, w: 0, h: 0, visible: false });
await P.until(async () => {
    snapshot = await P.thumbnailOf(cfg.servedB);
    return typeof snapshot === 'string' && snapshot.length > 0 && snapshot !== report.thumbnail.before;
}, 8000);
```

The cleanest variant: serve a third page `/c`, commit it, hide *without* letting the
STOP settle window elapse first, and assert the row gains a snapshot only after the
hide. Whichever shape is chosen, the run recorded as proof for G-14.1.1-6 must be one
where removing `:2355-2364` goes red.

### CR-02: A self-test plant is scored by a substring that an unrelated failure already contains

**File:** `scripts/verify-web-tab-live.mjs:1370` (case), `:1398` (matcher), `:966` (the
colliding message)

**Issue:** Plant scoring is `failures.some(f => f.includes(testCase.expect))`. The
`store-unread` case uses `expect: 'row'`. The string `row` is a substring of
`browsing` (`b-**row**-sing`), and the context assertions emit:

```js
report.failures.push(`expected exactly one top-level browsing context carrying ${cfg.servedA} ...`);
```

so any session in which the overlay context is not found scores the `store-unread`
plant as "red, naming 'row'" without the store assertion having fired at all. The
plant can pass for the wrong reason, which is the defect class CLAUDE.md's
verification rules were written against. The same loose matching makes
`focus-keyed-pill` and `state-ignored` (`expect: 'pill'`) satisfiable by the unrelated
`'the address pill does not have focus after "+"'` at `:1135`, and `no-geometry`
(`expect: 'rect'`) satisfiable only by the alignment message, which is skipped
entirely when the overlay context is never found — so that case is brittle in the
other direction.

**Fix:** Match on a stable, unique prefix rather than a bare word, and give every
failure message a namespaced prefix the way `lost-view:`, `dropdown:`, `restore:` and
`thumbnail:` already do:

```js
// message
failures.push(`store: no row for ${report.servedB} was readable through ChromeBarSuggestionService...`);
// case
{ name: 'store rows unread', plant: 'store-unread', expect: /^store: /, ... }
// matcher
if (!failures.some(f => (testCase.expect instanceof RegExp ? testCase.expect.test(f) : f.startsWith(testCase.expect)))) { ... }
```

Anchor `pill` to the two distinct pill assertions (`after the first commit the pill
reads` / `after the second commit the pill reads`) so the two plants that share it are
still distinguishable from a pill-focus failure.

### CR-03: `openDependent` throws a user-facing error carrying an internal command id, and the new copy gate is blind to it

**File:** `theia/extensions/modes/src/browser/setups-service.ts:510-514`

**Issue:**

```ts
throw new Error(
    'powerbrowser.setups.open-dependent: this tab cannot open in a dependent window -- ' +
    'choose a tab with hosted content (a terminal or an editor) and invoke the command again from the command palette'
);
```

This is thrown out of a command handler, so Theia surfaces the message verbatim in a
notification. CLAUDE.md `## User-facing copy` is unambiguous: *no internal identifier
may appear in user-facing text*, and 14-UI-SPEC.md:186-188 repeats it ("no pref key,
sentinel, port, URI-scheme internals, table name, or raw exception text"). The leading
`powerbrowser.setups.open-dependent:` is a command id.

The gate added in this phase would catch exactly this shape — `internalsOf`'s
`[A-Za-z]{2,}(?:\.[A-Za-z0-9_]{2,}){2,}` arm is what self-test plant 3
(`verify-gui09-setups-copy.mjs:424-428`) proves red on
`powerbrowser.setups.delete` — but `derivedServiceCopy` enumerates only `this.flash(`
arguments, `prompt`/`placeHolder` identifiers, the `ConfirmDialog` fields and
`pickSetup` literals. A `throw new Error(...)` is not a paint site it knows about, so
the one real violation in the file the gate guards is invisible to it. The string is
also uncontracted (no row in 14-UI-SPEC.md's Copywriting Contract), so it should have
surfaced as "unreviewed copy" as well.

**Fix:** Two halves. Replace the message with contracted copy that names the product
and drops the id, and add a table row for it:

```ts
throw new Error(
    'Power Browser can\'t open this tab in its own window. Choose a tab with hosted content — a terminal or an editor — and try again.'
);
```

Then teach the gate about the paint site, so the class cannot come back:

```js
// Paint site 5: messages thrown out of a command handler, which Theia surfaces verbatim.
for (const m of src.matchAll(/throw new Error\(\s*((?:'(?:[^'\\]|\\.)*'\s*\+?\s*)+)\)/g)) {
    copy.push(normaliseSlots([...m[1].matchAll(/'((?:[^'\\]|\\.)*)'/g)].map(x => unescapeLiteral(x[1])).join('')));
}
```

### WR-01: A *refused* open reads as success — `reply.ok !== true` diverges from `lostReply()`

**File:** `theia/extensions/tab-uris/src/browser/web-tab.ts:362-363`, `:507-513`;
`powerbrowser/shell/PowerBrowserAPI.sys.mjs:1629`

**Issue:** `handleGroupMutation` wraps *every* `webTabOpen` outcome in `ok: true` and
carries the real outcome in `where` (`:1629`), so a `refused-scheme` open returns
`{ ok: true, where: 'refused-scheme' }`. Both open-reply handlers test
`reply.ok !== true`:

```ts
void this.channel.request({ kind: 'webTabOpen', ... }).then(reply => this.setLostView(reply.ok !== true));  // :362
this.setLostView(reply.ok !== true);                                                                        // :509 reopen()
```

so a refused open *clears* the lost-view state. `settle()` (`:516-519`) does not have
this problem — it goes through `lostReply()`, which also folds `where ===
UNKNOWN_TAB_OUTCOME`. The result of the divergence: a refused open leaves
`hasPage === true`, an empty state node, the URL painted in the tab title and caption,
and no signal at all to the user. Not reachable from the address pill today
(`typedAddressTargetOf` normalises everything it accepts to `http(s)://`), but
reachable from any programmatic `WebTabOpenHandler.openUrl`, from `reopen()`, and from
the setups-restore opener path.

**Fix:** Use the one helper in all three places and give it the open vocabulary:

```ts
protected static lostReply(reply: WebTabReply): boolean {
    return reply.ok !== true
        || reply.where === UNKNOWN_TAB_OUTCOME
        || reply.where === 'refused-scheme';
}
// :362 and :509
this.setLostView(WebTabWidget.lostReply(reply));
```

### WR-03: `derivedDialogClasses` matches every `addClass` in the service, but reports them as dialogs

**File:** `scripts/verify-gui09-setups-copy.mjs:276-279`, `:344-349`

**Issue:** The regex is `/\.addClass\(\s*'([^']+)'\s*\)/g` over the whole file — it
has no way to tell `dialog.addClass(...)` from `someWidget.addClass(...)`. The
`length > 1` branch then reports "tags N dialogs with a class", which would be a false
red with a misleading message the first time this service styles any non-dialog
widget. Related: paint site 3 uses `src.indexOf('new ConfirmDialog({')` plus a
600-character magic window (`:207-209`), so a second confirmation in the same file is
invisible and a dialog options block that grows past 600 chars silently loses fields.

**Fix:** Anchor to the receiver and drop the magic window:

```js
return [...src.matchAll(/\bdialog\.addClass\(\s*'([^']+)'\s*\)/g)].map(m => m[1]);
```

and walk *every* `new ConfirmDialog({ ... })` by brace matching (the parser in
`verify-shell-gbrowser-standin.mjs:151-192` already does this correctly and can be
lifted) rather than slicing a fixed 600 bytes from the first one.

### WR-04: Paint site 2 silently drops copy it cannot resolve, while paint site 1 records it

**File:** `scripts/verify-gui09-setups-copy.mjs:198-204`

**Issue:**

```js
for (const m of src.matchAll(/\b(?:prompt|placeHolder|placeholder)\s*:\s*(\w+)\s*[,}]/g)) {
    if (consts.has(m[1])) { copy.push(consts.get(m[1])); }
}
```

An identifier that names no exported constant is dropped with no `unresolved.push`,
unlike every other paint site — and a *string literal* (`placeHolder: 'Pick one'`)
never matches `(\w+)` at all, so it never enters the derived set and never shows up as
unreviewed copy. A gate whose entire value is set equality has a silent hole on one
side of the set.

**Fix:** Handle the literal form and record the unresolvable identifier, matching the
discipline of paint site 1:

```js
for (const m of src.matchAll(/\b(?:prompt|placeHolder|placeholder)\s*:\s*(?:'((?:[^'\\]|\\.)*)'|(\w+))\s*[,}]/g)) {
    if (m[1] !== undefined) { copy.push(unescapeLiteral(m[1])); continue; }
    if (consts.has(m[2])) { copy.push(consts.get(m[2])); continue; }
    if (m[2] !== 'placeHolder') { unresolved.push(m[2]); }  // the pickSetup forward stays exempt, by name
}
```

### WR-05: The gBrowser gate's "required" side is scoped by a hand-kept three-file list

**File:** `scripts/verify-shell-gbrowser-standin.mjs:73-86`;
`scripts/verify-platform.sh:3681-3696`

**Issue:** The header and the registry comment both claim the row is "Red on an
upstream rebase adding a call". It is red only on a rebase that adds a call *inside
one of three enumerated files*. `UPSTREAM_CALL_SITES` is a hand-kept scope selector,
and unlike `EXPECTED_ENV_TOUCHERS` in the sibling gate it is not compared as set
equality against anything derived — a fourth privileged upstream module that starts
calling `gBrowser.foo()` against the shell window is invisible, and the resulting
TypeError-per-overlay is exactly the symptom G-14.1.1-19 was raised for. The
`DEAD SURFACE` half compounds this: because the assertion is equality, the stand-in is
forbidden from carrying a member that only a *fourth* file calls, so the correct
pre-emptive fix would itself go red.

**Fix:** Derive the scope. Walk the privileged upstream trees the shell window is
actually reachable from and take every file containing a `gBrowser`-receiver call:

```js
// e.g. upstream/browser/actors/**, upstream/toolkit/content/widgets/**,
// upstream/browser/base/content/** -- enumerated by directory, not by file
const files = walk(['upstream/browser/actors', 'upstream/toolkit/content/widgets'])
    .filter(f => /\.(mjs|js|sys\.mjs)$/.test(f) && GBROWSER_CALL.test(readSource(f)));
```

If a full walk is too broad, keep the file list but state in the header and the
registry comment that the assertion is scoped, so nobody reads the row as
rebase-complete coverage.

### WR-06: The backend-env gate is blind to untracked files — the trap CLAUDE.md records by name

**File:** `scripts/verify-backend-env-readers.mjs:142-146`

**Issue:** `collectTrackedFiles` walks `git ls-files`. CLAUDE.md's residual-brand
section records this exact trap for `scan-brand-residue.mjs`: "**An unstaged new file
is invisible to it** — stage before you trust a green scan." The same is true here and
the header does not say so, while it does enumerate four other out-of-scope categories
in detail. A new backend module that reads `process.env.POWERBROWSER_*` passes this
`--quick` row green until someone stages it — and the whole point of the gate is that
such a module fails *silently* at runtime.

**Fix:** Document it in the header alongside the other scope statements, and surface it
in the PASS line so a green result is not read as stronger than it is:

```js
const untracked = spawnSync('git', ['-C', REPO_ROOT, 'ls-files', '-o', '--exclude-standard', '-z'], { encoding: 'buffer' });
const pending = untracked.stdout.toString('utf8').split('\0').filter(Boolean).filter(inScope);
if (pending.length) {
    console.error(`${NAME}: FAIL -- untracked backend file(s) in scope, invisible to git ls-files: ${pending.join(', ')}. Stage them before trusting this row.`);
    process.exit(1);
}
```

any try. Renaming or moving any of the eight source files produces an uncaught
`ENOENT` stack trace instead of the message the design promises, and the
`verify-platform.sh` row surfaces that as an opaque non-zero exit.

**Fix:**

```js
function read(rel) {
    try {
        return readFileSync(join(REPO_ROOT, rel), 'utf8');
    } catch (error) {
        throw new Error(`${rel}: cannot be read (${error.code}) -- every expectation this check compares against is derived from it, so nothing below could mean anything`);
    }
}
// and wrap the derive() call
```

### WR-14: `publish()`'s rationale overstates what coalescing bounds

**File:** `theia/extensions/tab-uris/src/browser/web-tab.ts:448-459`

**Issue:** The comment says "The rAF coalescing and the `lastSent` dedupe above are
what bound the number of outstanding requests during a splitter drag." They bound it to
*one per animation frame* — the dedupe cannot help during a drag, because every frame
carries a genuinely different rect. Each surviving publish now registers a
`GROUP_RESPONSE_EVENT` listener on `window` and a 5000 ms timer
(`WEB_TAB_ACK_TIMEOUT_MS`, `:203`), and each of those listeners runs for every response
delivered while it is alive, so a sustained drag can hold on the order of 300 live
listeners per web tab, each doing an identity compare on every reply. The change from
`send` to `request` in this phase is correct for G-14.1.1-4; the sentence justifying
its cost is not.

**Fix:** Correct the comment, and add the bound it claims — keep at most one geometry
request in flight per widget and re-publish on settle:

```ts
if (this.geometryInFlight) { this.geometryPending = msg; return; }
this.geometryInFlight = true;
void this.channel.request(msg).finally(() => {
    this.geometryInFlight = false;
    if (this.geometryPending) { const next = this.geometryPending; this.geometryPending = undefined; void this.channel.request(next); }
});
```

### WR-15: `deleteSetup` leaks the dialog when `open()` throws, and carries a dead initialiser

**File:** `theia/extensions/modes/src/browser/setups-service.ts:466-479`

(with `confirmed` declared `let confirmed: boolean | undefined;`).

### WR-17: `persistLastSession` can overwrite a store it failed to read

**File:** `theia/extensions/modes/src/browser/setups-service.ts:835-854`

**Issue:**

```ts
try {
    const raw = (await this.fileService.read(this.setupsUri)).value;
    ...
} catch {
    if (name === null) { return; }
}
await this.fileService.write(this.setupsUri, JSON.stringify({ ..., setups, ... }));
```

When the read fails and `name !== null`, the method falls through and writes
`this.lastGoodSetups` over the file. `reloadSetups` (`:784-794`) treats the identical
read failure as "a mid-save race: keep last good, leave the session untouched" and
deliberately does *not* write. The write path takes the opposite view of the same
signal, so a setup saved by a concurrent writer (or by the other window in a dependent
session) between this process's last successful read and this write is silently
dropped. `onStop()` calls this on every shutdown, which is the likeliest moment for a
concurrent write to be in flight.

**Fix:** Treat an unreadable store as a reason not to write, matching the reader:

```ts
} catch {
    // A read failure here is the same mid-save race reloadSetups keeps last good on:
    // writing our stale copy over it would drop whatever the other writer just wrote.
    return;
}
```
