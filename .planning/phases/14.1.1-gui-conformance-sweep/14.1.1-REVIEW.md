## Critical Issues

### CR-01: The build-order gate is blind to side-effect imports — the exact defect class it exists to catch

**File:** `scripts/verify-theia-build-order.mjs:131` (`derivedImports`), asserted in the header at
`:26-30` and in the PASS line at `:283`

**Issue:** `derivedImports` only matches specifiers preceded by the `from` keyword:

```js
for (const m of src.matchAll(/\bfrom\s*['"]@powerbrowser\/([a-z0-9][a-z0-9-]*)/g)) {
```

A TypeScript **side-effect import** — `import '@powerbrowser/chrome-bar/lib/browser/x';` — is a
real import statement, creates a real compile-time dependency on the imported extension's `lib`
tree, and carries no `from`. It is therefore invisible to the edge derivation, to the
backwards-edge assertion, and to the declared-edge assertion simultaneously.

Reproduced against the working tree: prepending
`import '@powerbrowser/chrome-bar/lib/browser/chrome-bar-commands';` to
`theia/extensions/branding/src/browser/powerbrowser-mark.ts` creates a forward edge from chain
index 0 (`branding`) to chain index 6 (`chrome-bar`) that is also undeclared in `branding`'s
manifest — two failures of the two assertions the gate exists for. The gate printed:

```
verify-theia-build-order: PASS -- 8 chain entries equal 8 extension directories ...
and all 6 derived @powerbrowser edges point backwards in the chain and are declared ...
```

exit 0. (The plant was reverted; `git diff` on that file is clean.)

The header's stated contract at `:26-30` — "the EDGES -- for each extension, the other extensions
it imports" — is therefore false, and the restriction's own justification ("a bare
`@powerbrowser/<name>` occurrence anywhere else is deliberately NOT accepted: prose comments ...
mint phantom edges") does not require dropping side-effect imports. The right discriminator is the
`import`/`export` **statement**, not the `from` keyword.

**Fix:** Match both specifier positions, keeping the prose-comment exclusion:

```js
const SPECIFIER = /(?:\bfrom\s*|\bimport\s*(?:type\s*)?|\bexport\s*)['"]@powerbrowser\/([a-z0-9][a-z0-9-]*)/g;
// ...
for (const m of src.matchAll(SPECIFIER)) {
```

and add a `--self-test` plant (h) that writes a side-effect forward import into a scratch copy of
one extension's `src` and requires a `backwards edge:` red naming it — the same shape as plant (a),
but exercising the specifier form plant (a) cannot reach.

### CR-02: The setups-copy gate reads only the FIRST `ConfirmDialog`, so a second dialog's copy is unreviewed and its missing destructive class invisible

**File:** `scripts/verify-gui09-setups-copy.mjs:221-235` (paint site 3), `:377-383`
(destructive-ink half), `:407` (PASS line); claim falsified at
`theia/extensions/modes/src/browser/modes.css:590-600`

**Issue:** Paint site 3 locates dialog copy with a single `indexOf` and a fixed 600-char slice:

```js
const dialogAt = src.indexOf('new ConfirmDialog({');
if (dialogAt >= 0) {
    const dialog = src.slice(dialogAt, dialogAt + 600);
```

Only the first dialog in the file is ever read. Its `title` / `ok` / `cancel` literals and its
`msg` template are the only dialog copy the gate can see, so a **second** `ConfirmDialog` anywhere
later in the service is not user copy as far as the gate is concerned — its strings are neither
compared against the Copywriting Contract nor scanned by `internalsOf`.

Reproduced against the working tree: appending a second method to `SetupsService` containing

```ts
const d = new ConfirmDialog({ title: 'Wipe everything?', msg: 'gone forever', ok: 'Wipe', cancel: 'Nope' });
```

with **no** `addClass` produced:

```
verify-gui09-setups-copy: PASS -- 18 painted setups strings, derived from five paint sites,
match 18 contracted literals as set equality, no internals in copy,
destructive ink scoped to exactly one dialog
```

exit 0. Four uncontracted user-facing strings shipped past a gate whose whole claim
(header `:36-38`) is "the gate goes red on an addition AND on a removal". (Plant reverted;
`git diff` on the service is clean.)

This also makes the replacement claim plan 09 wrote into `modes.css` when it retired the pass-1
WR-02 claim false in turn:

```
   ... the real invariant is one class per destructive dialog, which the
   service-side assertion already covers ...
```

It does not cover it. `derivedDialogClasses` counts `.addClass(` calls, so a second destructive
dialog that adds **no** class leaves `dialogClasses.length === 1` and the gate green. Pass 1's WR-02
was answered by narrowing the comment to a claim that is also untrue.

**Fix:** Iterate every dialog, and derive the class *per dialog* rather than counting `addClass`
calls file-wide:

```js
for (const m of src.matchAll(/new ConfirmDialog\(\{([\s\S]*?)\}\)\s*;/g)) {
    const dialog = m[1];
    for (const f of dialog.matchAll(/\b(?:title|ok|cancel)\s*:\s*'((?:[^'\\]|\\.)*)'/g)) {
        copy.push(unescapeLiteral(f[1]));
    }
    const msg = dialog.match(/\bmsg\s*:\s*(\w+)\(/);
    // ... resolve through templates as today
}
```

Then add a self-test plant 9 that inserts a second `ConfirmDialog` with uncontracted copy and
requires an `unreviewed copy` red naming one of its literals. Replacing the fixed 600-char slice
with the matched literal also closes IN-01 below.

### CR-03: Pass-1 WR-01 is recorded closed but only half-fixed — the second inline spelling is still in the tree

**File:** `theia/extensions/tab-uris/src/browser/web-tab.ts:363` (unfixed) vs `:509-514` (fixed);
false closure record at `.planning/phases/14.1.1-gui-conformance-sweep/14.1.1-UAT.md:1004`

**Issue:** Pass 1's WR-01 named **two** sites reading an open reply with the inline
`reply.ok !== true` test: `:362-363` (`onAfterAttach`) and `:509` (`reopen`). Plan 09
(`bfdb979`) changed only `reopen`, and wrote a comment there asserting the other reading no longer
exists:

```ts
// `lostReply()`, never a second inline spelling: an `ok: true` reply
// naming the unknown-tab outcome would otherwise read here as a
// successful reopen and leave the body blank. Two spellings of "this
// reply means chrome no longer renders the tab" is how the two drift
// apart -- the defect G-14.1.1-4 closed one site earlier.
this.setLostView(WebTabWidget.lostReply(reply));   // :514
```

while line 363 still reads:

```ts
void this.channel.request({ kind: 'webTabOpen', tabId: this.tabId, url: this.url })
    .then(reply => this.setLostView(reply.ok !== true));   // :363
```

The UAT records this as closed — "the inline test routed through the class's own `lostReply()`
predicate, **leaving one reading**" (`14.1.1-UAT.md:1004`, gap G-14.1.1-48,
`closed_by: plan 14.1.1-09, commit bfdb979`). There are still two readings, and the surviving one
is on the **initial** open — the path every web tab takes on attach.

The underlying bug is unchanged and is confirmed by the chrome side: `handleGroupMutation` wraps
every `webTabOpen` outcome in `ok: true` and carries the real outcome in `where`
(`powerbrowser/shell/PowerBrowserAPI.sys.mjs:1629`), and `webTabOpen` can answer `"refused-scheme"`
(`:2166-2168`). A refused initial open therefore leaves `lostView === false`, so `renderState()`
paints `EMPTY_STATE_COPY` instead of `LOST_VIEW_COPY` and the user is given no signal and no Reload
affordance. Pass 1 also asked for `'refused-scheme'` to be folded into `lostReply()`; that was not
done at any site.

**Fix:** Route line 363 through the same predicate and give the predicate the open vocabulary:

```ts
protected static lostReply(reply: WebTabReply): boolean {
    return reply.ok !== true
        || reply.where === UNKNOWN_TAB_OUTCOME
        || reply.where === REFUSED_SCHEME_OUTCOME;
}
// :363
    .then(reply => this.setLostView(WebTabWidget.lostReply(reply)));
```

`publish()`'s deliberately narrower unknown-tab-only arm at `:456` stays as it is — its rationale
at `:420-424` is sound and should keep its comment saying so. Then correct
`14.1.1-UAT.md:1004`: either flip G-14.1.1-48 back to open, or re-close it on the commit that
actually leaves one reading.

### WR-01: Two shipped plants produce identical failure sets, so neither red is attributable — the guard checks expect strings, not red sets

**File:** `scripts/verify-web-tab-live.mjs:1516-1534` (`expectTableFaults`), `:1583-1584` and
`:1619-1620` (the two plants)

**Issue:** Plan 07's guard rejects an unanchored expect and a *shared* expect, and its comment
states the reason: "a SHARED expect makes two plants indistinguishable, so neither one's red says
anything about the fault it planted." Distinct expect strings do not achieve that property. Two
plants in the shipped table drive the identical code path to the identical failure set:

- `popup` replaces `WebTabOpenHandler.prototype.openUrl` with a `window.open` fallback (`:498-502`).
- `newtab-popup` replaces the New Tab command handler with `window.open` (`:636-643`).

The New Tab command routes `handler.open(uri)` (`chrome-bar-commands.ts:146-151`) and
`WebTabOpenHandler.open` immediately delegates to `this.openUrl(...)`
(`web-tab.ts:594-596`), so both plants produce exactly:

1. `the setup phase threw at step [new tab]: ... "+" produced no web-tab widget ...`
2. `popup: window.open was called 1 time(s) ...`
3. `newtab: "+" produced no web-tab widget in the main area ...`

`popup` is scored on `popup:` and `newtab-popup` on `newtab:`, but each would score green on the
other's expect. Swapping the two expects leaves the self-test passing, which is the operational
definition of "these two reds prove nothing about which fault caused them".

**Fix:** Extend the guard from expect-string uniqueness to red-set distinguishability. The cheapest
form that needs no extra sessions: record each plant's full failure family set during the run and,
after the loop, require that for every ordered pair of plants at least one plant's expect is absent
from the other's family set:

```js
const families = new Map(); // plant -> Set of family prefixes seen
// ... after each plant's assertReport:
families.set(testCase.plant, new Set(failures.map(f => f.split(':')[0] + ':')));
// ... after the loop:
for (const [p, fam] of families) {
    for (const [q, other] of families) {
        if (p !== q && other.has(expectOf(p)) && fam.has(expectOf(q))) {
            fail(`plants '${p}' and '${q}' each satisfy the other's expect -- neither red is attributable`);
        }
    }
}
```

Then either delete one of the two plants or give `newtab-popup` a distinguishing observable
(e.g. assert the `popup` plant leaves the New Tab *command* handler intact).

### WR-02: Four of the fifteen declared failure families have no plant, including the family that is entirely absence assertions

**File:** `scripts/verify-web-tab-live.mjs:1229-1264` (the fifteen families), `:1578-1621` (eleven
plants)

**Issue:** The header declares fifteen families. The case table plants eleven. The four with no
plant are `nav:`, `walk:`, `close:` and `shell:`. Two of those matter:

**Fix:** Add at least a `close:` plant — e.g. a `close-leaks-row` plant that overrides

### WR-03: Broken-instrument messages share the contract prefixes, so a plant can be credited for a broken instrument

**File:** `scripts/verify-web-tab-live.mjs:1240` vs `:1259-1263`; the messages at `:766`, `:851`,
`:1378`, `:1388-1389`, `:1417`

**Issue:** The file states the rule twice and the two statements contradict each other. At
`:1259-1263`:

> NOT in the set, deliberately: the derivation failures ..., a plant that could not be applied, and
> a phase that threw. Those three report a BROKEN INSTRUMENT rather than a contract ... and **no
> plant may be scored on them**.

But five broken-instrument messages are emitted *with* a family prefix and therefore *are* in the
set — and `:1240` says so explicitly for one of them ("align: ... and its own no-pair-measured
broken-instrument guard"):

| line | message prefix | what it reports |
|---|---|---|
| `:766` | `lost-view:` | the widget exposes no state node |
| `:851` | `thumbnail:` | no store row for the hanging page appeared |
| `:1378` | `walk:` | the tab was current after none of the hops |
| `:1388` | `align:` | no rect pair could be measured at all |
| `:1417` | `thumbnail:` | the row already carried a snapshot before the hide |

Since scoring is `failures.some(f => f.startsWith(expect))`, any plant expecting one of those four
prefixes can be credited by a message that says the instrument broke rather than that the contract
failed. No shipped plant is currently scored that way (checked case by case), so this is latent
rather than live — but it is the same defect class plan 07 fixed, one level down.

**Fix:** Give broken-instrument messages their own reserved prefix and exclude it from scoring:

```js
const BROKEN = 'instrument:';
// e.g.  fail(`${BROKEN} align: no overlay/placeholder rect pair could be measured ...`);
// and in selfTest:
if (failures.some(f => f.startsWith(BROKEN))) { /* report as could-not-be-driven, never as a score */ }
```

Then reconcile `:1240` with `:1259-1263` so the file states the rule once.

### WR-04: The newly contracted `SETUP_DEPENDENT_UNSUPPORTED` copy is unreachable, and its next step names an affordance the code says does not exist

**File:** `theia/extensions/modes/src/browser/setups-service.ts:140-147`, `:516-524`;
`theia/extensions/modes/src/browser/setups-commands.ts:35-37`, `:55-57`;
`.planning/milestones/v1.3-phases/14-modes-windows-setups/14-UI-SPEC.md:207`

**Issue:** Paint site 5 was added on the premise that "Theia renders a thrown command error
verbatim, so a thrown string is user copy". For this one throw the premise does not hold, because
the command has no user-reachable invocation at all:

- `SETUPS_OPEN_DEPENDENT` is declared with an `id` and **no `label`**
  (`setups-commands.ts:35-37`), so it never appears in the command palette.
- There is no `MenuContribution` and no `KeybindingContribution` anywhere in
  `theia/extensions/modes/src/browser/`.
- `grep -rn 'SETUPS_OPEN_DEPENDENT\|open-dependent'` over `theia/extensions/**` (excluding `lib/`)
  finds only the four lines that *declare and register* it. Nothing executes it.

So `openDependent()` is a dead surface, and the string it throws can never reach a screen.

Second, the copy's own next step is self-contradicting. The shipped literal ends
"...then try again", while the doc comment two lines above it (`:143-145`) and the UI-SPEC row it
was written from (`14-UI-SPEC.md:207`) both state:

> It names no command id — the command carries no palette label, so re-invoking it is not an
> affordance the user has; the only real next step on screen is selecting a different tab.

CLAUDE.md requires the next step to be "a real affordance on screen". "Try again" names an action
the same paragraph says the user cannot perform. The gate cannot catch this: it compares the
service literal against the spec literal, and plan 09 wrote both in the same commit.

**Fix:** Either wire the command to a real affordance (a `label`, a menu item, or a tab context
action) and keep the copy, or drop the trailing clause so the copy names only the step that exists:

```ts
export const SETUP_DEPENDENT_UNSUPPORTED = 'Power Browser can\'t open this tab in its own window. Select a terminal or editor tab first.';
```

updating `14-UI-SPEC.md:207` in the same change so the gate stays green. If the surface is meant to
stay dormant until a later phase, record it in `deferred-items.md` rather than shipping contracted
copy for it.

### WR-05: The live check derives the channel class positionally — the first plain `export class` in the file

**File:** `scripts/verify-web-tab-live.mjs:197-200`

**Issue:** Two of the three class derivations pin on a structural property
(`implements OpenHandler`, `extends BaseWidget`). The third does not:

```js
const channelClass = /export class (\w+)\s*\{/.exec(webTab)?.[1];
```

It resolves to whichever plain exported class comes first in `web-tab.ts` — today
`WebTabChannel` at `:158`, by position alone. A new exported class declared above it (a small
value type, an options holder) silently re-points every `channelClass` consumer:
`P.channel = __getByName(container, cfg.channelClass)` in the setup phase, the
`state-ignored` plant's landed guard, and `P.hideOverlay`'s `send`. The derivation would still be
non-empty, so the "a zero derivation is a named FAIL" guard at `:198-200` would not fire — the
check would fail as "the setup phase threw", which names no drift and is not scoreable by any
plant.

**Fix:** Pin it on the same kind of structural property the other two use, and assert the shape:

```js
const channelClass = /export class (\w+)\s*\{[\s\S]*?\bregister\s*\(/.exec(webTab)?.[1];
```

or, cheaper and stricter, require the derived name to be the class that registers the state
listener:

```js
if (channelClass && !new RegExp(`class ${channelClass}[\\s\\S]*?addEventListener\\(WEB_TAB_STATE_EVENT`).test(webTab)) {
    failures.push(`${WEB_TAB_REL}: the derived channel class '${channelClass}' does not install the ${stateEvent} listener -- the derivation has drifted onto a different class`);
}
```
