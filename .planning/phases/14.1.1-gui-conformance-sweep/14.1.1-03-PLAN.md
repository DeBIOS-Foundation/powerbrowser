<objective>
Close two `minor` GUI conformance gaps in the setups surface: **G-14.1.1-21** (a failed setup save
or delete must say the save or delete failed, not the restore) and **G-14.1.1-22** (the Delete Setup
confirm button must render in the destructive colour the spec reserves for it).

Purpose: one constant is currently reused for three different failures, and the delete case tells
the user to delete the thing that just failed to delete. The destructive-ink rule shipped in Phase
15 for Panorama's confirm and Phase 14's only destructive dialog never received one.

Output: two new contracted copy strings, one new scoped CSS rule, and a new `--quick` copy gate
with a `--self-test` that pins both strings by set equality against the spec's copy table.
</objective>

<threat_model>
Security enforcement is active at **OWASP ASVS level 1**, blocking threshold **high**. This plan
installs no npm/pip/cargo package, so no package-legitimacy checkpoint applies.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caught write exception → user-facing flash | A privileged failure detail can leak into a user surface |
| User-typed setup name → dialog body and store | Untrusted text rendered in a confirmation and persisted |
| Destructive-action styling → user's mental model | A mis-signalled button invites an unintended irreversible action |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14.1.1-03-01 | Information disclosure | The two new failure strings in `setups-service.ts` | medium | mitigate | Both are fixed literals with no interpolation of the caught error, no file path, no store URI. Pinned verbatim by `gui09-setups-copy` set equality and re-checked by the gate's no-internals shape predicate and by `shell-error-copy-no-internals`. |
| T-14.1.1-03-02 | Spoofing | User-typed setup name rendered in the Delete confirmation body | low | accept | `setupDeleteBody` renders through the stock `ConfirmDialog` `msg` field as text, and the name is already capped and trimmed on the way in. Carried Phase 14 behaviour; this plan changes styling and failure copy only, not the render path. |
| T-14.1.1-03-03 | Tampering | Destructive ink applied to a non-destructive dialog | low | mitigate | The CSS rule is scoped to the new class alone, and the gate asserts exactly one setups dialog carries a destructive class — a second one goes red. |
| T-14.1.1-03-04 | Repudiation | A failed delete that reports success would leave the user unsure what happened | medium | mitigate | The delete-failure string states the setup is still in the list, and the existing early `return` after the flash leaves `lastGoodSetups` and `currentSetup` untouched, so the message and the state agree. |
</threat_model>
