### CR-01 confirmed and strengthened — G-14.1.1-6's proof is vacuous

The reviewer's mechanism is correct, and the tree makes it worse than stated. The
`thumbnail` phase (`verify-web-tab-live.mjs:751-772`) hides the overlay, then polls:

```js
snapshot = await P.thumbnailOf(cfg.servedB);
return typeof snapshot === 'string' && snapshot.length > 0;
```

No baseline, no clear. I traced the phase order from the source object literal:
`newTab`(584) → `commitA`(616) → `commitB`(631) → `dropdownAfterEnter`(665) →
`lostView`(684) → `modeWalk`(720) → `storeRows`(736) → `thumbnail`(751).

By the time `thumbnail` runs, `servedB` has had a snapshot written **three separate ways**:

1. `commitB` loads `servedB` → network STOP → `scheduleSettleCapture` at `:2263`.
2. `lostView`'s Reload re-opens and reloads `servedB` → a second STOP.
3. `modeWalk`'s five hops each hide and re-show the overlay → the **hide-time arm at
   `:2365`** fires repeatedly, several phases before the thumbnail phase's own hide.

`TAB_THUMBNAIL_SETTLE_MS` is 500 ms; the mode walk alone far exceeds it. The `P.until`
predicate is therefore satisfied on its first poll. Deleting the hide-time block at
`:2358-2365` leaves all three thumbnail assertions green — the phase does not test what its
header says it tests.

The check documents a *different* limitation honestly and that note is correct, but it does
not cover this one: the `thumb-not-scheduled` plant strips the **read** (`P.thumbnailOf`
replaced at `:564`), not the schedule. Its own comment says so. So **no plant in this
instrument exercises any capture site.** What the check does still prove is the
`findTabBrowserForUri` overlay branch — remove that and `captureTabThumbnail` returns
`no-live-tab`, writes NULL, and the assertions go red. G-14.1.1-6 is therefore half-proved,
and the "last-view" half — the part the gap's own truth names — is unproved.
