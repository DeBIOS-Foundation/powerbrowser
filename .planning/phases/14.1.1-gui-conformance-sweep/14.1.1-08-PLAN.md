<objective>
Close **G-14.1.1-9**. `theia/package.json`'s `build:extensions` hand-orders the chain as branding
→ tab-uris → customize → telemetry → token-gate → modes → chrome-bar → backend-opencode, while
`theia/extensions/tab-uris/src/node/tab-query-service.ts:26` imports
`@powerbrowser/token-gate/lib/node/powerbrowser-env` and `.gitignore` ignores `theia/**/lib/`. On
a clean checkout the chain builds `tab-uris` against a `token-gate/lib` that does not exist yet.
It works on this machine only because `token-gate/lib` is already on disk.

There is a second, quieter half of the same defect, implied by the gap's own root cause when it
offers "build via workspace topological order" as an alternative fix: `tab-uris` does not declare
`@powerbrowser/token-gate` in its `package.json` at all. A topological build would not have saved
it either, because the edge is invisible to the workspace graph. Both halves are fixed here.

Purpose: a hand-kept ordering can only ever agree with the tree it was copied from — the class
CLAUDE.md's second verification rule exists against. The fix is not a longer chain; it is a gate
that derives the chain and the edges independently from the tree and compares them.

Output: a corrected chain, a declared dependency, one new derive-and-compare gate with a
fault-planting self-test, and exactly two new rows on the one registry.

**`theia/extensions/tab-uris/src/node/tab-query-service.ts` is RESERVED** — it belongs to the
concurrent session. Read it to confirm the import; do not modify it. The fix does not need it.
</objective>

  </read_first>
  <action>
Write `scripts/verify-theia-build-order.mjs`, a Node script with the same shape as the other
derive-and-compare gates: a default run and a `--self-test` run, an unrecognised argument exits 2,
a one-line PASS verdict carrying its own counts.

Derive three things independently, and treat an empty derivation on any of them as a named FAIL
rather than a skip:
1. **the chain** — the ordered list of extension directory names parsed out of
   `build:extensions` in `theia/package.json`;
2. **the extension set** — the directory names actually present under `theia/extensions`;
3. **the edges** — for each extension, the set of other extensions it imports, taken ONLY from
   import and export specifiers of the form `from '@powerbrowser/<name>...'` in its own
   `src` tree, self-references dropped. Do not accept a bare `@powerbrowser/<name>` occurrence
   anywhere else in the file; prose comments carry that string and would mint phantom edges.

Then assert four things:
- **chain equals extension set**, compared as set equality in both directions, so a new extension
  that nobody added to the chain and a chain entry whose directory was deleted are both red;
- **no duplicate** appears in the chain;
- **every edge points backwards** — for each importer and each extension it imports, the
  imported extension's chain index is strictly less than the importer's; the failure names both
  extensions, both indices and one importing file, so the reader can act on it without re-deriving;
- **every edge is declared** — the imported extension appears in the importer's own
  `package.json` `dependencies` (or `peerDependencies`), because an undeclared workspace edge is
  the same defect one step earlier: it is invisible to the workspace graph, so no topological
  build order could rescue it either.

The `--self-test` copies the tree's real inputs into a scratch directory made with `mkdtemp` and
removed in a `finally`, plants one fault per case, and requires each to go red naming the drift:
(a) swap the chain positions of an extension and one it imports — must name the backwards edge;
(b) drop one extension from the chain — must name the set-equality failure;
(c) name a directory in the chain that does not exist — must name the set-equality failure from
the other side; (d) add a second chain entry for an extension already in it — must name the
duplicate; (e) remove one workspace dependency from an importer's manifest while leaving the
import in place — must name the undeclared edge; (f) empty the chain entirely — must fail as a
broken instrument rather than pass vacuously; (g) empty the extensions directory listing — same.
Print an `ok` line per case and a single PASS or FAIL verdict.

The check reads text only. It runs in milliseconds, needs no dev shell, spawns no build, and is
therefore honestly a `--quick` row rather than a heavier tier. Say that in the header, and say in
the same paragraph what it does NOT prove: that a clean-checkout `yarn build:extensions` actually
succeeds. It proves the ordering and declaration invariants that build depends on. Name the
deferral and its reason — the concurrent session's `lib` trees — so a later reader does not
mistake the row for the build itself.
  </action>
