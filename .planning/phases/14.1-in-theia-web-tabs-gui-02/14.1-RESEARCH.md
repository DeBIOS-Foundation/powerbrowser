## Summary

The overlay bridge needs no new Gecko file, no patch, no new npm package, and no new Theia extension. Everything lands in files that already exist: `PowerBrowserAPI.sys.mjs` gains a web-tab host (create/geometry/navigate/back/forward/reload/close plus a progress listener that both writes `tabs.sqlite` rows and pushes state), `GroupActorChild.sys.mjs` gains a five-line `receiveMessage` that re-dispatches a chrome push as a content-compartment `CustomEvent`, and `@powerbrowser/tab-uris` gains one new source file holding the placeholder widget, its `WidgetFactory`, an `http:`/`https:` `OpenHandler`, and the geometry publisher. The chrome bar is rewired from the F9 stock-window sink to the web-tab path, and `chromeBarHasNavigableTab()` starts returning whether the shell's current widget is a web tab.

Step 1 of GUI-02 (an overlay `<xul:browser>` rendering `example.com` inside the shell window over the live frontend) is recorded as CONFIRMED on 2026-09-06 (`GUI-DEFECTS.md` item 1); the spike code is not in the tree, so this research re-derives the mechanics from upstream source rather than from the spike. The chrome-side coordinate mapping is the identity: the Theia frame is `position: fixed; inset: 0` in the shell document, both frames share one window (one `devicePixelRatio`), and no zoom UI exists in the shell, so a placeholder rect measured in the Theia frame is the overlay's rect in the chrome document, offset only by the Theia frame's own `getBoundingClientRect()` (which is `0,0` today and cheap to add for robustness).

Three findings change how the plan must be shaped. (1) `check-internals-boundary.sh --catalogue` matches catalogue rows by **exact `PowerBrowserAPI.sys.mjs:<line>`**, so every new forbidden-pattern occurrence needs a row and every insertion above existing occurrences renumbers rows below it; insert the new methods immediately after `startTabStoreTriggers` (ends at `:2017`) so only two rows (`:2026`, `:2068`) shift. (2) `scripts/verify-chrome-bar-suggestions.mjs` asserts the widget imports `OPEN_BROWSER_WINDOW_COMMAND_ID` and plants against the string `await this.commands.executeCommand(OPEN_BROWSER_WINDOW_COMMAND_ID, url);` — rerouting commits makes that gate red and its self-test report "never applied its fault"; the gate's expectation must be retargeted in the same plan. (3) A body-portalled Theia layer (the chrome bar's own suggestion dropdown, the command palette, dialogs) paints inside the Theia frame and is therefore **occluded by the overlay** wherever they overlap; the frontend must include "no blocking layer is open" in the visibility it publishes, or Phase 13's suggestion dropdown disappears behind the page the moment a web tab is active.

**Primary recommendation:** Reuse the `PowerBrowserGroupRequest` channel with `webTab*` kinds and a `PowerBrowserWebTabState` push; put the widget/factory/open-handler in `@powerbrowser/tab-uris`; write store rows chrome-side from the progress listener keyed by page URL; ship one new `--quick` derive-and-compare script and one new BiDi live script, each with `--self-test` plants; end every plan with a cache-purged launch confirmed in Chris's window.

### Pattern 1: Overlay creation (chrome side, inside `PowerBrowserAPI`)

**What:** Build the `<xul:browser>` exactly as `tabbrowser.js` does, minus the tabbrowser-only hooks, and set every attribute **before** appending — the frameloader is created in `connectedCallback → construct()` `[VERIFIED: upstream/toolkit/content/widgets/browser-custom-element.mjs:397-406, 1090]`.

**Attributes and why (all read from upstream):**

- `type="content"` — content docshell `[VERIFIED: tabbrowser.js:2750]`.
- `remote="true"` + `remoteType="web"` — `isRemoteBrowser` is `hasAttribute("remote")` `[VERIFIED: browser-custom-element.mjs:545-547]`; `remoteType` attribute set alongside `remote` `[VERIFIED: tabbrowser.js:2764-2767]`; `"web"` is `E10SUtils.DEFAULT_REMOTE_TYPE` `[VERIFIED: upstream/toolkit/modules/E10SUtils.sys.mjs:25-35]` — quoted: `const WEB_REMOTE_TYPE = "web";` … `const DEFAULT_REMOTE_TYPE = WEB_REMOTE_TYPE;`.
- `maychangeremoteness="true"` — **required**, or every cross-site navigation aborts its process switch: `[VERIFIED: upstream/netwerk/ipc/DocumentLoadListener.cpp:1860-1867]` quoted: `if (browserElement && !browserElement->HasAttribute(u"maychangeremoteness"_ns)) { MOZ_LOG(... "Process Switch Abort: toplevel switch disabled by <browser>"); return false; }`. Under Fission the first `https://` load from a `web` browser is such a switch. `tabbrowser.js:2757-2759` sets it whenever `gMultiProcessBrowser || remoteType`.
- `manualactiveness="true"` — without it the browsing context's activeness follows the shell window and cannot be turned off for hidden overlays: `[VERIFIED: upstream/docshell/base/BrowsingContext.cpp:821-830]` (`if (!aEmbedder->HasAttr(nsGkAtoms::manualactiveness)) { … SetExplicitActive(isActive …) … bp->SetRenderLayers(isActive); }`). With it, `browser.docShellIsActive = bool` sets `browsingContext.isActive` and `remoteTab.renderLayers` `[VERIFIED: browser-custom-element.mjs:503-514]`.
- `messagemanagergroup="browsers"` — copied from `tabbrowser.js:2748`; harmless and keeps parity with stock web browsers. `message="true"` is a tabbrowser message-manager hook and is not needed `[ASSUMED]`.
- `tabindex="-1"` — matches the Theia frame (`powerbrowser.xhtml:48`).
- **Do not** set `primary="true"` (that is the Theia frame, `window.content`), `contextmenu`, `tooltip`, or `autocompletepopup` (they name `browser.xhtml` elements that do not exist here).
- `permanentKey` via `PowerBrowserAPI.createPermanentKey()` (`:488-490`) and a push into `window.gBrowser.tabs` (`powerbrowser.js:63-64` shape `{ tabs: [{ linkedBrowser }] }`) — this is what makes the overlay a WebDriver-addressable top-level context: BiDi's `TabManager.getTabBrowser(win)` returns `win.gBrowser` `[VERIFIED: upstream/remote/shared/TabManager.sys.mjs:80-90]` and reads `tab.linkedBrowser` `[VERIFIED: :40]`; `NavigableManager` returns a null id without `permanentKey` (`INTERNAL-APIS.md` row `:489`). The live check depends on this.

**Placement and stacking:** the shell document is HTML with the XUL namespace declared on the root (`powerbrowser.xhtml:19-20`), and its content frame is `#powerbrowser-content { position: fixed; inset: 0; z-index: 0; }` `[VERIFIED: powerbrowser/shell/powerbrowser.css:215-223]`; the loading layer is `z-index: 1` (`:12-14` region), error `z-index: 2` (`:60-63`), diagnostics `z-index: 3`. Overlays therefore go on `<body>` after the content frame with `position: fixed; z-index: 1` — above Theia, below the error and diagnostics layers. `powerbrowser.js` already creates XUL elements in this document (`document.createXULElement("keyset")`, `:274-285`), so `createXULElement("browser")` from chrome code holding the Theia frame's `ownerDocument` is the same path. A XUL `<stack>` is not needed: CSS absolute/fixed positioning in the HTML document is already how the content frame is placed.

**Coordinates:** the frontend sends CSS px from `placeholder.getBoundingClientRect()`. Chrome applies `left = theiaFrame.getBoundingClientRect().left + x` (and likewise `top`), `width = w`, `height = h`. ### Pattern 3: Progress listener that writes rows and pushes state

`browser.addProgressListener(listener, mask)` defaults the mask to `NOTIFY_ALL` `[VERIFIED: browser-custom-element.mjs:957-963]`; pass `Ci.nsIWebProgress.NOTIFY_LOCATION | Ci.nsIWebProgress.NOTIFY_STATE_NETWORK` (`NOTIFY_LOCATION = 0x80` `[VERIFIED: upstream/uriloader/base/nsIWebProgress.idl:95]`; `NOTIFY_STATE_ALL = 0x0f` `[VERIFIED: :67]`). In-tree JS example: `[VERIFIED: upstream/browser/base/content/test/chrome/test_aboutCrashed.xhtml:31-32 — QueryInterface: ChromeUtils.generateQI(["nsIWebProgressListener", "nsISupportsWeakReference"])]`. Keep a strong reference in the host `Map` or the listener is collected (same class of bug as `pendingTimers`, `PowerBrowserAPI.sys.mjs:40-43`).

- `onLocationChange(webProgress, request, location, flags)` `[VERIFIED: nsIWebProgressListener.idl:540]`: act only when `webProgress.isTopLevel`; ignore `LOCATION_CHANGE_SAME_DOCUMENT` (`0x1`, `[VERIFIED: :516]`) for row writes (a hash change is not a new tab), still push it for the pill.
- `onStateChange(webProgress, request, stateFlags, status)` `[VERIFIED: :442]`: `loading = !!(stateFlags & STATE_START)` when `STATE_IS_NETWORK` is set; `STATE_START = 0x1`, `STATE_STOP = 0x10`, `STATE_IS_NETWORK = 0x40000` `[VERIFIED: :58, :62, :132]`.

- Back/forward state: `browser.canGoBack` / `canGoForward` read `webNavigation` `[VERIFIED: browser-custom-element.mjs:429-443]`; `goBack()` honours `navigationRequireUserInteraction` (`:860-873`), `reload()` is `LOAD_FLAGS_NONE` (`:886-895`).

**Store writes (SC4):** key `uri = url` for `^https?://` locations only (skip `about:blank`, so a bare "+" does not pollute suggestions). On a top-level location change to a different spec: `removeTabRow(previousUri)` then `writeTabRow({ uri: spec, url: spec, title, chromeWin })`; on `pagetitlechanged`: `writeTabRow` again; on `webTabClose`: `removeTabRow(uri)`. `writeTabRow`'s signature is `{ uri, url, title, lastActive, chromeWin }` and it upserts by `uri` `[VERIFIED: PowerBrowserAPI.sys.mjs:908-923]`; the private-window filter reads `chromeWin` — pass the shell window (never private). Known ceiling, same as the stock `webview:`+URL rule (`browser-tab-uri.ts:26-27`): two web tabs on one URL share one row, and closing either deletes it. The 7-day sweep (`pruneClosedTabRows`, `:1682-1698`, called from `sweepTabStoreFromSessionStore` `:1886-1898`) only deletes rows with `last_active` older than `TAB_STORE_CLOSED_RETENTION_MS` (`:152`, 7 days) that are not in the sessionstore live set — in-shell rows are not in sessionstore, so a row that is never re-touched ages out after 7 days; the explicit `removeTabRow` on close is what keeps the store honest before then.

### Pattern 4: The Theia widget, factory, open handler

- `WEB_TAB_FACTORY_ID = 'powerbrowser.web-tab'`; options `{ id: string; url: string }`. `id` is a per-session counter and lives **only** in the construction options, never in the URI — `docs/URI-SCHEMES.md:16-40` general rule: "Non-user-chosen discriminators never appear in an address … stays in the widget's construction options, never in the URI." Without the counter, `WidgetManager`'s dedup by `{factoryId, options}` would collapse two tabs on one URL into one widget.
- `WebTabWidget extends BaseWidget`: empty `node` with a dark background (so a hidden overlay shows a plain surface, not white), `title.label` = page title or URL, `title.caption` = URL, `title.closable = true`, `title.iconClass = 'codicon codicon-globe'`. Do **not** implement `ExtractableWidget` (`isExtractable`/`secondaryWindow`, `[VERIFIED: @theia/core/lib/browser/widgets/extractable-widget.d.ts:8-10]`): the overlay cannot follow a widget into a dependent window, and an un-extractable widget is simply not offered the move. Do **not** implement `StatefulWidget` (`storeState/restoreState`, `[VERIFIED: shell-layout-restorer.d.ts:16-24]`): cross-launch layout restore is moot because the frontend origin (port) changes every launch (`GUI-DEFECTS.md` "Corrections"), and named setups restore tabs through the opener anyway (`setups-service.ts:648-651 — open(this.opener, new URI(tab))`).
- Lifecycle hooks that fire on the widget `[VERIFIED: @lumino/widgets/types/widget.d.ts:309 onResize, :344 onAfterShow, :351 onBeforeHide; @theia/core/lib/browser/widgets/widget.d.ts:62 onCloseRequest, :65 onBeforeDetach, :66 onAfterAttach]`: `onAfterAttach` → `webTabOpen` + publish; `onResize`/`onAfterShow`/`onBeforeHide`/`onBeforeDetach` → publish; `onCloseRequest` → `webTabClose` then `super`. ### Anti-Patterns to Avoid

- **Reading `dispatchEvent`'s return value as "chrome took it."** Measured false twice (`browser-window-command.ts:89-98`, `PowerBrowserAPI.sys.mjs:1557-1574`). Web tabs need no fallback decision: with no chrome host the widget simply shows its empty node.
- **Passing `Cu.cloneInto`, `Services`, or any privileged name into `GroupActorChild.sys.mjs`.** The child's contract is zero privileged reach (`:15-18`); the `--quick` boundary scan covers `powerbrowser/` minus the API file and would fail.
- **Editing `powerbrowser.js` to hold overlay logic.** `createXULElement("browser")` itself is DOM, but `Ci.nsIWebProgress.*`, `Services.scriptSecurityManager`, `ChromeUtils.generateQI`, `getActor`, `permanentKey` minting are internals; keep the whole host in `PowerBrowserAPI` and have `handleGroupMutation` reach the shell document through the actor's embedder element. No new chrome file means no `jar.mn` row and no tier-2 build.
- **Hand-keeping the kind list in a gate.** Derive `case "webTab…"` labels from `PowerBrowserAPI.sys.mjs` and the `kind: 'webTab…'` literals from `web-tab.ts`; compare set-equal both ways.
- **Setting `browser.src` or reusing `loadURIInBrowser` (system principal) for a page URL.**
- **Appending the overlay before setting `remote`/`remoteType`/`maychangeremoteness`/`manualactiveness`** — the frameloader reads them at connect.
- **Putting the tab counter or any internal id in the tab label or pill.** `shell-error-copy-no-internals` is pattern-based and the 01-UI-SPEC rule is global.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-process page rendering | An iframe (`@theia/mini-browser`) | Chrome-owned `<xul:browser remote>` | `X-Frame-Options`/`frame-ancestors` blank most sites (01-RESEARCH.md:397); a real docshell is not framed |
| Navigation state | Polling `currentURI`/`contentTitle` | `nsIWebProgressListener` + `pagetitlechanged` | Event-driven, same as `tabbrowser.js` |
| Privileged→content object hand-off | Property copying | `win.JSON.parse(JSON.stringify(...))` in the content window (existing child pattern) | Xray wrappers hide own properties (item 10 defect 5) |
| Ack correlation | A new correlator | The existing request/response event pair; fire-and-forget for geometry | One channel, one origin wall |
| Tab store schema/writes | New table or second connection | `writeTabRow`/`removeTabRow` | Single-writer invariant |
| Opening `https:` URIs from Theia | A command per call site | `OpenHandler` at priority 1000 | Setups restore, Panorama dive, links, and the chrome bar all route through `OpenerService` already |
| Live driving of the built shell | A new harness | `withFirefoxPage('')` in `scripts/lib/firefox-bidi.mjs` (`:277-320`) | Headless, empty URL, `--remote-allow-system-access`, stdout tee |

**Key insight:** the overlay is a fourth kind of Firefox tab host (after `browser.xhtml`, DevTools toolbox hosts, and PiP), and every one of them builds the same `<browser>` with the same attributes; the only genuinely new code is the geometry publisher and the two message directions, both of which reuse a proven channel.

## Common Pitfalls

### Pitfall 1: Catalogue rows are matched by exact line number
**What goes wrong:** `internals-catalogue` goes red on every existing occurrence below an insertion point in `PowerBrowserAPI.sys.mjs`.
**Why it happens:** `check_catalogue_consistency` greps the catalogue for `PowerBrowserAPI\.sys\.mjs:<line>([^0-9]|$)` for each occurrence line it derives `[VERIFIED: scripts/check-internals-boundary.sh, check_catalogue_consistency / catalogue_occurrence_lines]`. Non-forbidden rows (e.g. `:817`, `GUI-DEFECTS.md` item 14) are not enforced, which is why that one is stale without failing.
**How to avoid:** insert the web-tab host between `startTabStoreTriggers` (ends `:2017`) and `isInitialLaunch` (`:2025`) so only `:2026` and `:2068` shift; add rows for each new `Ci.`/`Services.` line (`Ci.nsIWebProgress.NOTIFY_*`, `Ci.nsIWebProgressListener.STATE_*`, `Services.scriptSecurityManager.createNullPrincipal`); run `scripts/check-internals-boundary.sh --catalogue` and fix each `file:line` it names.
**Warning signs:** `internals-catalogue: FAIL -- N occurrence(s) with no catalogue row`.

### Pitfall 2: Stale chrome script or stale Theia bundle
**What goes wrong:** the edit appears absent; a live test "fails" against old code (this invalidated the F9 test).
**Why it happens:** Gecko's startup cache serves the previously compiled `powerbrowser/shell/*.mjs`; `theia build` output is what the backend serves.
**How to avoid:** chrome edit → `rm -rf objdir/tmp/profile-default/startupCache` + `MOZ_PURGE_CACHES=1 ./objdir/dist/bin/powerbrowser -purgecaches`; Theia edit → extension build + app build + backend restart. The BiDi harness uses a fresh `mkdtemp` profile (`firefox-bidi.mjs:286`) so it never sees a stale profile cache, but it does see a stale bundle.
**Warning signs:** no `CHILD_MODULE_LOADED`-class log lines; behaviour identical to before the edit.

### Pitfall 3: Overlay occludes Theia's own body-level layers
**What goes wrong:** the chrome bar's suggestion dropdown (portalled to `document.body`, `chrome-bar-widget.tsx:492-497`), the command palette, and dialogs vanish behind the page whenever a web tab is active.
**Why it happens:** the overlay is a separate OS-composited layer above the whole Theia frame; nothing drawn inside the frame can appear above it.
**How to avoid:** publish `visible: false` while a blocking layer is attached (Pattern 4). Upgrade path if the flash is unacceptable: send the blocking layer's rect and apply `clip-path: polygon(evenodd, …)` to the overlay chrome-side — more code, defer until asked. `[ASSUMED: the occlusion itself is certain from the stacking design; the chosen policy is a judgment call]`
**Warning signs:** typing in the pill shows no dropdown while a web tab is active.

### Pitfall 4: Process switch silently refused
**What goes wrong:** the first `https://` load stays in the `web` process or fails to render under Fission.
**Why it happens:** missing `maychangeremoteness` `[VERIFIED: DocumentLoadListener.cpp:1860-1867]`.
**How to avoid:** set it before append. **Warning signs:** `Process Switch Abort: toplevel switch disabled by <browser>` in `MOZ_LOG=ProcessIsolation:4`.

### Pitfall 5: Hidden overlays keep painting and running timers
**What goes wrong:** every open web tab renders and runs at full activity; the page under another tab still plays video/audio.
**Why it happens:** without `manualactiveness`, activeness follows the shell window `[VERIFIED: BrowsingContext.cpp:821-830]`.
**How to avoid:** `manualactiveness="true"` and `docShellIsActive = visible` on every geometry/visibility message; hide with `style.visibility = 'hidden'` (the `tabpanels` deck idiom, `xul.css:453-470`), never `display: none` or element removal.

### Pitfall 6: `window.open`/`target=_blank` from a page opens a stock OS window
**What goes wrong:** a link with `target=_blank` inside a web tab opens `browser.xhtml`, not a new in-shell tab.
**Why it happens:** the shell window has no `nsIBrowserDOMWindow`; `nsContentTreeOwner::ProvideWindow` returns with no context and the watcher creates a new chrome window `[VERIFIED: upstream/xpfe/appshell/nsContentTreeOwner.cpp:475-530]`. This is the same path GUI-01 relies on (`powerbrowser.js:287-300`).
**How to avoid:** accept this phase (it is GUI-01's contract) and record it; the fix is an `nsIBrowserDOMWindow` on the shell window routing `OPEN_NEWTAB` into `webTabOpen` — a later phase.

### Pitfall 7: Suggestions gate anchors on the F9 routing
Covered in Pattern 5. **Warning signs:** `verify-chrome-bar-suggestions --self-test: 'planted re-spelled window-command id' never applied its fault`.

### Pitfall 8: Page focus swallows Theia keybindings
**What goes wrong:** with a web page focused, `Ctrl+L` (`chrome-bar-keybindings.ts:24-26`) and every Theia shortcut stop working until the user clicks Theia.
**Why it happens:** the focused docshell is the overlay's; Theia never sees the key.
**How to avoid:** accept this phase; the mechanism if needed is a `<key reserved="true">` in the shell (pattern at `powerbrowser.js:274-285`) that pushes a `focusAddress` state event through the same child. `[ASSUMED]`

### Pitfall 9: Content prompts and context menus in overlays
**What goes wrong:** `alert()` inside a page falls back to a window-modal prompt or logs an error; right-click does nothing.
**Why it happens:** tab-modal prompts need `gDialogBox`/tab dialog boxes the shell does not have — `Prompter.sys.mjs:975-1015` falls back to `MODAL_TYPE_WINDOW` when internal dialogs are unavailable; the `contextmenu` attribute is not set because `browser.xhtml`'s menu does not exist here. `[VERIFIED for the fallback code path; the observed behaviour in this shell is ASSUMED — verify live]`
**How to avoid:** record as known limitations; verify `alert()` once in Chris's window.

### Pitfall 10: Concurrent session and unstaged files
**What goes wrong:** `scan-brand-residue` passes on a green tree that has an unstaged new file; another session's `.planning` edits get swept into a commit.
**How to avoid:** `git add` new files before trusting `--quick`; commit with explicit paths.

    onLocationChange(wp, req, location, flags) {
      if (!wp.isTopLevel) return;
      const spec = location.spec;
      if (!(flags & Ci.nsIWebProgressListener.LOCATION_CHANGE_SAME_DOCUMENT) && /^https?:\/\//i.test(spec)) {
        if (entry.uri && entry.uri !== spec) PowerBrowserAPI.removeTabRow(entry.uri).catch(() => {});
        entry.uri = spec;
        PowerBrowserAPI.writeTabRow({ uri: spec, url: spec, title: b.contentTitle, chromeWin: win }).catch(() => {});
      }
      PowerBrowserAPI.webTabPush(theiaBrowser, tabId, b, b.webProgress.isLoadingDocument);
    },
    onStateChange(wp, req, stateFlags) {
      if (!wp.isTopLevel || !(stateFlags & Ci.nsIWebProgressListener.STATE_IS_NETWORK)) return;
      PowerBrowserAPI.webTabPush(theiaBrowser, tabId, b, !!(stateFlags & Ci.nsIWebProgressListener.STATE_START));

    PowerBrowserAPI.webTabPush(theiaBrowser, tabId, b, b.webProgress.isLoadingDocument);
  });

  return PowerBrowserAPI.webTabNavigate(tabId, url);
},

webTabNavigate(tabId, url) {
  const spec = typeof url === "string" && url ? url : "about:blank";
  if (spec !== "about:blank" && !/^https?:\/\//i.test(spec)) return "refused-scheme";
  const entry = webTabs.get(tabId);
  if (!entry) return "unknown-tab";
  entry.browser.fixupAndLoadURIString(spec, {
    triggeringPrincipal: Services.scriptSecurityManager.createNullPrincipal({}),
  });
  return "loading";
},

webTabGeometry(theiaBrowser, tabId, { x, y, w, h, visible }) {
  const entry = webTabs.get(tabId);
  if (!entry) return "unknown-tab";
  const host = theiaBrowser.getBoundingClientRect();   // (0,0) today; keeps the mapping honest if the frame ever moves
  Object.assign(entry.browser.style, {
    left: `${host.left + x}px`, top: `${host.top + y}px`, width: `${w}px`, height: `${h}px`,
    visibility: visible ? "visible" : "hidden",
  });
  entry.browser.docShellIsActive = !!visible;
  return "applied";
},

webTabPush(theiaBrowser, tabId, b, loading) {
  theiaBrowser.browsingContext.currentWindowGlobal.getActor(GROUP_ACTOR_NAME).sendAsyncMessage("PowerBrowserWebTabState", {
    tabId, url: b.currentURI.spec, title: b.contentTitle, loading: !!loading,
    canGoBack: b.canGoBack, canGoForward: b.canGoForward,
  });
},

## Open Questions

1. **How should the live check distinguish "opened an overlay" from "opened a stock window"?**
   - What we know: both add one top-level BiDi context; the overlay's context is exposed only because the host pushes into `window.gBrowser.tabs`.
   - What's unclear: whether a stock window's tab would appear in the same `getTree` result set ordering.
   - Recommendation: assert on geometry (`mozInnerScreenX/Y` alignment with the placeholder) — a stock window's tab cannot align with the placeholder rect — plus `POWERBROWSER_SHELL_READY` count unchanged via the stdout tee (`firefox-bidi.mjs:277` `stdoutPath`).

2. **Should `webTabGeometry` be acked?**
   - What we know: `sendQuery` round-trips every request; the response for an unregistered id is dropped.
   - Recommendation: fire-and-forget with rAF coalescing; if profiling shows cost, teach the child to `sendAsyncMessage` for that one kind.

3. **Does `firefox-bidi.mjs` expose a way to re-query the context tree after a tab is opened?**
   - What we know: `withFirefoxPage` hands the callback `evaluate`, `waitFor`, `screenshot`, `topLevelContexts` (`:472, :513`); `resolveUrlContext(topLevelContexts, url)` exists (`:149`).
   - What's unclear: whether `topLevelContexts` is a live getter or a snapshot.
   - Recommendation: Wave 0 reads the helper and, if needed, adds a `contexts()` re-query; the `--self-test` of the live script proves it.

4. **Row key collisions for two tabs on one URL.**
   - Recommendation: accept (same ceiling as the stock `webview:` rule); mark with a `ponytail:` comment naming the upgrade (a stable per-tab key requires a schema change, out of scope).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A loopback page opened inside an overlay drives the actor channel (child loads under `matches: http://127.0.0.1/*`, host check passes) | Spoofing / Elevation | Require the sender's `browsingContext.top.embedderElement` to carry `primary="true"` (the Theia frame); reject otherwise |
| Web load with the system principal (file:/chrome: reach) | Elevation | Null principal via `createNullPrincipal({})`; never `loadURIInBrowser`; scheme wall before any load |
| Overlay positioned over the chrome bar or diagnostics layer by a malformed geometry message | Tampering | Only the Theia frame can send geometry (wall above); clamp to the shell window; error/diagnostics layers stay at higher `z-index` |
| Page title/URL injected into Theia UI | Tampering (XSS) | Set `title.label`/`caption` and the pill `value` as text, never HTML (React text nodes); chrome bar already treats suggestion titles as text (13-03 threat notes) |
| Overlay outlives its widget (orphan process, audio keeps playing) | DoS | `webTabClose` on `onCloseRequest`; chrome also drops overlays when the Theia frame's WindowGlobal is destroyed (`actor.didDestroy`) |
| Token leakage | Information disclosure | No new surface: pushes carry URL/title/booleans only; the per-launch token is never in any message |
