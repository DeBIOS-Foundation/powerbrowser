<locked_decision name="theia-to-chrome-group-mutation-transport">
**Adopted: new JSWindowActor pair (`PowerBrowserGroup`) into new
`PowerBrowserAPI` group methods.** Tree-verified rationale:

- Theia backend (Node) can never open `tabs.sqlite` read-write: the
  second-writer gate (`scripts/verify-sql-store-second-writer.mjs` rules
  a/b) fails any such line BY DESIGN, and WAL coordination would corrupt at
  runtime. So extending the `TabQueryService` RPC shape with write methods
  is rejected: the backend has nowhere lawful to send the write.
- A backend→chrome forward (staging file swept by chrome, or HTTP) is
  rejected: chrome serves no HTTP to the backend, and a staging file needs
  an invented poll/ack protocol with murky failure semantics — it cannot
  serve the contracted save-error Retry/revert ack cleanly.
- `window.open`-style (candidate A, GUI-01) is rejected: one-way
  fire-and-forget, no ack, no payload discipline; proven nav-only in
  `powerbrowser/shell/powerbrowser.js:287-305`.
- The actor pair is the only sanctioned content→chrome crossing with
  request/response ack (rollback/retry for free). Pre-approved as the
  candidate-B fallback in 01-05; the content browser is
  `remote="true" remoteType="web"`
  (`powerbrowser/shell/powerbrowser.xhtml:48`), so the actor loads where
  Theia runs.

Correction to the plan brief: `ChromeUtils.registerWindowActor` coverage
does NOT need adding — plan 08-03 already landed it as an unconditional
`FORBIDDEN_PATTERNS` entry (`scripts/check-internals-boundary.sh:56`) with

<actor_wire_format>
Child→parent `sendQuery("PowerBrowserGroupMutation", msg)` where msg is
`{ kind, id, ...fields }`, kind in `createGroup | setTabGroup |
moveGroup | resizeGroup | renameGroup | dissolveGroup | closeGroup |
setActiveGroup`. Parent→child: `{ ok: true, ...echo } | { ok: false,
reason: 'validation' | 'store' }`. Content side (Theia frontend is
unprivileged `http://127.0.0.1` web content — it cannot touch `ChromeUtils`
or `getActor`) bridges via DOM events: frontend dispatches
`PowerBrowserGroupRequest` CustomEvent `{ requestId, msg }`; child actor
options declare `events: { PowerBrowserGroupRequest: { capture: true } }`,
`handleEvent` forwards via `sendQuery`, then dispatches
`PowerBrowserGroupResponse { requestId, reply }` back. Frontend
`group-actor-client.ts` correlates by `requestId` with a **5s ack timeout**
(locks RESEARCH OQ1); rejection or timeout surfaces the contracted
save-error bar. Drag-move/resize streams debounce **150ms** (in-tree
`p-debounce` pin) with a final commit on pointerup. Chrome validates every
field (id non-empty, title trimmed + cut at 60, bounds finite numbers ≥0
clamped to sane max 10000, tab URIs opaque non-empty strings matched
against known rows); violations reject loudly naming method + id, never
stored. No `matches` restriction on registration (actor is lightweight);
chrome-side validation is the wall, documented in the threat model.
</actor_wire_format>
