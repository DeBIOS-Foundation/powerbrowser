<objective>
**As a** downstream brand author, **I want to** a single registered check that proves the generator
reproduces the hand-written build surfaces exactly, **so that** I can trust the manifest is the
source of truth and not merely claimed to be.

This is the phase's acceptance test made mechanical. Phase 1 deliberately wrote every branding value
as a hand-written literal so that Phase 2 would have something independent to compare against. This
plan spends that investment.

Purpose: byte-identity is the property that makes the whole generator credible, and a property that
is not registered as a check is a property that decays. It joins the one registry as two appended
rows.

Output: `scripts/verify-generated-identity.mjs`, its fault-planting self-test, and two rows in the
`--quick` array.
</objective>

    Two edits, in this order.

    A. Make `scripts/generate.mjs` importable. Add a main guard around the top-level dispatch so the
    module runs its CLI only when it is the entry point, comparing the resolved path of the current
    module against the first process argument path. Add named exports for the frozen target table,
    the config resolver that returns the merged and validated config, and the repo-root constant.
    Export nothing else — the check needs the emitter set and a resolved config, not the internals.
    Re-run the generator afterwards to confirm the guard did not change its behaviour as a CLI.

    B. Write `scripts/verify-generated-identity.mjs`, copying `verify-registry-shape.mjs`'s whole
    shape. Its header carries a rationale block in that file's style stating two things a future
    reader needs: why the ACTUAL emitter set is derived from the target table and only the EXPECTED
    five-file list is written down, and why this check emits into its own temporary directory rather
    than reading `generated/`. The second reason is the one that will not be obvious: `generated/` is
    git-ignored, so every fresh clone and every CI run starts without it, and a check that compared
    against it would be red on a tree with no defect. Also state, as that file does, that the check
    is honestly quick — no build, no browser, no display, no network.

    The check does four things:

      1. Set equality on the target list. `EXPECTED` is a frozen array of the five tracked paths —
         `.mozconfig`, both `powerbrowser/branding/{dev,release}/configure.sh`, and both
         `powerbrowser/*.desktop` files. This is the ONE hand-kept list, and it gets the comment
         explaining why one is permitted here: it is the declared contract, and the actual set is
         derived from the imported target table so the two can disagree. Compare as a set equality
         using a difference reporter that names surplus and missing entries by path, copied from the
         analog. A sixth emitter added without declaring it goes red; a declared file whose emitter
         was deleted goes red too.

      2. Emit into `mkdtempSync` under the OS temp dir with a descriptive prefix, removed in a
         `finally`. Iterate the imported target table, run each emitter over the resolved config and
         the entry's variant, and write into the temporary directory. Never write to `generated/` and
         never read from it.

      3. Byte-compare each emitted file against its tracked counterpart in the repo. Report every
         difference, one indented line each, under a counted banner. Compare bytes; a line-level diff
         may be computed for the failure message only.

      4. Assert `generated/` is git-ignored and that git tracks nothing under it: `git check-ignore`
         on the directory must succeed, and `git ls-files` scoped to it must return empty output. Use
         the repo's existing `execFileSync` idiom for git invocations. These are GEN-04's other half
         and they belong on this row rather than in a third script.

    Add the non-vacuity guard before reporting a pass: if the temporary emission produced zero files,
    fail with a message saying the comparison proves nothing. A clean diff of nothing against nothing
    must never read as a pass.

    Failure banner names what to do if the change was deliberate, in the analog's style: the five
    hand-written files are the independent comparand and are not edited to make this check green —
    the emitter is what changes. Pass line carries a count of files compared.

    Do not create a sibling driver script and do not add a test framework. This repo has one
    verification driver and one registry; adding a check means appending a row, which Task 2 does.
  </action>

    A. The `--self-test`. Structure it exactly as `verify-registry-shape.mjs` does.

    Start with a clean-baseline guard: run the comparison over the unmodified target table and bail
    with the explicit "the unmodified tree is already red, so the planted-fault results below would
    be meaningless" message if it is not green. Planted-fault results measured against an already-red
    baseline prove nothing.

    Then a frozen case table of seven cases, each carrying a name, a mutated target table, and an
    `expect` string the failure output must contain:

      - five drift cases, one per target, each built by wrapping that entry's emitter so its returned
        string differs from the real one by a single byte. Expect the failure to name that entry's
        tracked path. Wrap rather than edit a file on disk: the five tracked files are the
        independent comparand and this phase does not touch them.
      - one surplus case: a sixth entry whose tracked path is not in the declared list. Expect the
        failure to name that surplus path.
      - one missing case: the table with one entry removed. Expect the failure to name the removed
        tracked path.

    Per case, assert the mutation actually landed before running the check — a planted fault that did
    not change its input makes the case vacuous, and a vacuous case that reports `ok` is worse than
    no case. Require the failure output to CONTAIN the case's `expect` string, not merely to be
    non-empty. Print one `ok` line per case naming the case and the string it went red on, then a
    counted PASS line.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| generator output → verification claim | The gate's own honesty is the asset. A check that cannot go red is a false claim of correctness, which is worse than no claim. |
| git-ignored state → CI verdict | A gate reading ignored state produces a verdict that depends on what a previous run happened to leave behind. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-14 | Spoofing | the byte-identity gate as a non-discriminating instrument | high | mitigate | Seven planted faults, each required to go red naming the specific drift; a clean-baseline guard that refuses to report when the unmodified tree is already red; a mutation-landed guard per case; and a non-vacuity guard that fails a comparison over an empty emission. The gate's own registry row for its self-test rides beside it in `--quick`. |
| T-02-15 | Tampering | hand-kept expectation list drifting into agreement with any tree | high | mitigate | The ACTUAL emitter set is derived from the imported target table at check time and compared to the declared five-file list as a set equality, so the check goes red on an addition AND on a removal. The one permitted hand-kept list carries the comment explaining why it is permitted. |
| T-02-16 | Tampering | gate depending on git-ignored `generated/` | high | mitigate | The check emits into its own `mkdtempSync` directory and compares against the five TRACKED files. An acceptance criterion runs it with `generated/` deleted and requires exit 0. |
| T-02-17 | Tampering | importing `generate.mjs` executing its CLI as a side effect | medium | mitigate | A main guard around the top-level dispatch, with an acceptance criterion asserting that importing the module writes no file and does not exit the process. |
