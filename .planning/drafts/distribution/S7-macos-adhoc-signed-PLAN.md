<objective>
Produce a macOS universal DMG on the Linux runner, ad-hoc signed and not notarized, with the Theia sidecar and a pinned Node runtime inside the bundle, one universal MAR behind two Darwin descriptors, and a human Mac session as the gate that lets the asset join a Release.

Purpose: this is the last per-OS artifact stage. Every task after the first depends on two facts the probe establishes, namely which macOS toolchain parts this host can actually assemble and whether the three darwin sidecar natives are obtainable without a Mac. Nothing here procures an Apple Developer Program membership, notarizes anything, or relaxes the elevated-updates trust requirement.
Output: probe record, `.#firefox-macos` shell, two macOS target mozconfigs, the five missing macOS branding inputs, universal build plus DMG plus MAR plus two descriptors, staged darwin sidecar, download-page copy and its gate, deferred pointers, and the Mac install-matrix record.

Toolchain call, made from checked facts rather than assumption. nixpkgs `cctools` 1010.6 is published for `aarch64-darwin` and `x86_64-darwin` only, so no `cctools-port` exists for this host; `libdmg-hfsplus` and `hfsplus-tools` are absent from nixpkgs entirely; nixpkgs `apple-sdk` 14.4 is Darwin-only and is in any case below the `mac_sdk_min_version()` floor of `26.5` at `upstream/build/moz.configure/toolchain.configure:254-255`. What is present for `x86_64-linux` is `rcodesign` 0.29.0, `lld` 21.1.8, `llvm` 21.1.8 (which provides `llvm-lipo`, and `lipo -create -output` is exactly the call `upstream/python/mozbuild/mozpack/unify.py:84-85` makes), `rsync` 3.4.1, `cmake` 4.1.2, `openssl` 3.0.19, `zlib` 1.3.2, `gnupatch` 2.8 and `nodejs_22` 22.22.2. The pinned tree supplies what nixpkgs does not: `upstream/taskcluster/scripts/misc/unpack-sdk.py` is a self-contained sha512-verified SDK fetcher that takes the real URL when `MOZ_AUTOMATION` is unset, and `upstream/taskcluster/kinds/fetch/toolchains.yml:281-297` pins `libdmg-hfsplus` at revision `d6287b5afc2406b398de42f74eba432f2123b937` and `diskdev_cmds-540.1.linux3.tar.gz` at sha256 `b01b203a97f9a3bf36a027c13ddfc59292730552e62722d690d33bd5c24f5497`. Task 1 proves this assembles before task 2 writes a shell around it.

Two package-path facts are recorded here because each of them fails only after two tier-3 cross builds have already been paid for, and both were found by reading rather than by burning the builds.

- The cocoa package path consumes five branding files that `generated/branding/dev` and `generated/branding/release` do not carry. Three of them come from `upstream/toolkit/moz.configure:3992-3999`, whose DMG branch appends `--dsstore`, `--background` and `--icon` out of the branding directory into `MOZ_PACKAGE_EXTRA_ARGS`; `upstream/python/mozbuild/mozbuild/action/package.py:54-66` forwards each one, `make_dmg.py:34-40` turns them into extra files, and `upstream/python/mozbuild/mozpack/dmg.py:195-198` copies each with `shutil.copyfile` and no existence guard. The other two come from `upstream/browser/app/Makefile.in:85-87`, which copies `firefox.icns`, `document.icns` and `Assets.car` unconditionally. Only `firefox.icns` exists today. Task 3 emits `document.icns`, `Assets.car`, `dsstore`, `background.png` and `disk.icns`, and its gate derives the required set from both consumers rather than from one.
- Two independent `mach build` runs take two different build IDs: `upstream/build/variables.py:22-27` falls back to `datetime.now()` when `MOZ_BUILD_DATE` is unset or is not fourteen characters. `upstream/python/mozbuild/mozpack/unify.py:196-205` returns `None` for any differing non-binary file outside `**/*.manifest`, and `unify.py:220-271` special-cases only `buildconfig.html` and `install.rdf`, so `application.ini`, `platform.ini` and the preprocessed `Info.plist` (whose `MAC_BUNDLE_VERSION` comes from `buildid.h` through `upstream/browser/app/Makefile.in:67,76`) would each stop the unify step. Mozilla's own automation avoids this by setting one `MOZ_BUILD_DATE` per push across every build in it (`upstream/taskcluster/gecko_taskgraph/transforms/task.py:2642`). Task 4 does the same and asserts it.
