<objective>
Compile MAR signature verification back into every updater this tree builds, embed the fork's own certificates through one hook-only patch, sign every release MAR with a key that never reaches the build host, and give the release pipeline one descriptor emitter. SEC-02 and UPD-04.

Purpose: no build ships to the public with signature verification off. Today `.mozconfig:8` carries `--enable-unverified-updates`, which unsets `MOZ_VERIFY_MAR_SIGNATURE` and sets `DISABLE_UPDATER_AUTHENTICODE_CHECK` (`upstream/build/moz.configure/update-programs.configure:42-57`), so `updater.cpp:3063-3075` skips `VerifySignature` and `VerifyProductInformation` and `objdir/dist/bin/updater --channels-allowed` prints `Not Applicable: No support for signature verification` (observed live on the current tree). The MAR the last hop served carries zero signatures (`signmar -T .mozbuild/mar-hop/nplus1.mar` prints `Signature block found with 0 signatures`).

The built `objdir/dist/bin/update-settings.ini` also reads `ACCEPTED_MAR_CHANNEL_IDS=None`, but that is NOT an effect of the flag: `update-programs.configure:118-125` sets the value only from `depends_if("ACCEPTED_MAR_CHANNEL_IDS")`, and the tracked `.mozconfig` (16 lines) carries no such line, so the unset config var renders as the Python `None`. The channel value arrives from release-identity's mozconfig emission, which is why Task 1 claim F gates on it as a dependency rather than treating it as this stage's output.

Output: a claims record, two certificates under `brand/` with the human review re-signed, four generated comparands, patch 030, the flag gone from the generator, a rebuilt N and N+1 with verification compiled in, `scripts/sign-mar.sh`, `scripts/build-update-xml.mjs`, the hop verifier extended with signature and negative evidence, two registry rows, a three-drive proof (applied, failed: 19, failed: 22), and the docs that carry the custody and CI contract for linux-release-pipeline-and-update-channel.

Design calls recorded here rather than reopened later:

- The updater tries the primary certificate and then the secondary, one key per attempt (`archivereader.cpp:73-96`), and libmar requires every signature on the MAR to verify with a key count equal to the verified count (`mar_verify.c:281`), so a MAR carries exactly one signature. The secondary certificate is embedded now so a rotation to the offline secondary key needs no client rebuild.
- The certificates are branding inputs: the generator copies them into both variants' branding directories the way it copies the icon rasters, and the patch names them through `CONFIG["MOZ_BRANDING_DIRECTORY"]`. `upstream/browser/app/moz.build:182-187` is the precedent for reading that CONFIG value and joining a filename onto it; the sink here is a `GENERATED_FILES` input rather than a `DEFINES` string, so resolution runs through `SourcePath`'s leading-slash rule (`context.py:928-935`, join against topsrcdir then normpath). Either way the patch carries a substitution and no value.
- `updater --channels-allowed` cannot report the channel on Linux and never will: the branch is gated on `argc == 2` (`updater.cpp:3328`), so no install directory can be passed, and `gInstallDirPath` (declared `updater.cpp:334`) is not assigned until `updater.cpp:3546`, more than two hundred lines later in the same function. `PopulategMARStrings` therefore reads `/update-settings.ini` (`updater.cpp:3039`), fails, and returns `UPDATE_SETTINGS_FILE_CHANNEL` = 38 (`updatererrors.h:67`), which line 3336 prints as `Error: 38` with exit 1. A verifying build therefore prints `Error: 38`, an unverifying build prints `Not Applicable: No support for signature verification` with exit 0, and every check in this plan asserts the former exactly rather than asserting the absence of the latter.
- The wrong-channel plant mutates the test install's `update-settings.ini` instead of signing a second MAR, so the operator signs once. `PopulategMARStrings` reads that file from the install directory during a real update (`updater.cpp:3039`, reached from `UpdateThreadFunc` at 3051 after the install dir is set), so the mutation lands on code 22.
</objective>
