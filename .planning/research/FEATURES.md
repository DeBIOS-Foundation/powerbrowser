# Feature Research: v1.1 Hardening and SQL Tabs

**Domain:** Firefox-ESR-fork distribution hardening (installers, extensions, crash pipeline) + SQL-backed browser tabs
**Researched:** 2026-09-04
**Confidence:** MEDIUM-HIGH overall (canonical upstream docs + local tree reads; see Source Confidence)

**Scope:** ONLY the four v1.1 areas — (1) real installer builds PKG-01, (2) EXT-02 npm/local-path extension sources + WebExtensions declaration, (3) TEL-04 crash-report pipeline, (4) SQL-01 SQL-backed tabs. GUI-02/GUI-05 are explicitly deferred until after SQL tabs and are NOT scoped here. v1 carry-overs (release build, tier-3 fixture builds, ESR rebase drill, Theia re-pin, WINDOWS #13/#14) are execution work, not feature questions, and appear only as dependencies.

## Feature Landscape

### Area 1: Real installer builds (PKG-01)

v1 is schema-complete only: the generator emits a Linux-subset branding directory. PKG-01 means the full Windows + macOS packaging surfaces actually built on packaging hosts.

#### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| `mach package` producing the Windows full installer on a Windows host | Firefox's installer build is the only supported path to `setup.exe`: `mach package` → packaged app → NSIS compile of `installer.nsi` → 7-zip SFX concatenation. There is no cross-compile route — the installer build depends on Windows-only tools and must run on a Windows machine | HIGH | Requires a Windows packaging host (or CI runner). Uninstaller (`helper.exe`) builds during `mach build`, not the installer target. Depends on: branding-dir generator emitting the full Windows file set (`branding.nsi`, `wizHeader*.bmp`, `wizWatermark.bmp`, `firefox.ico`/`firefox64.ico`, `VisualElements*`, `stubinstaller/`, `msix/`) |
| `branding.nsi` + `defines.nsi` generated from `configuration.toml` identity | `installer.nsi` reads `BrandFullName`/`BrandShortName` from `branding.nsi` (InstallDir, version keys, `Name`) and build defines from `defines.nsi` (preprocessed from `defines.nsi.in` with `ACDEFINES`). A fork shipping Mozilla's names here installs into Mozilla's directory | MEDIUM | WR-04 pre-fix belongs here: reject bare `$VAR` in NSIS defines — an unexpanded variable in a define silently writes a wrong path/name into the installer. New generator surface + verify row |
| macOS DMG built via `mach package` on a macOS host with brand assets | macOS packaging = staged app bundle + `background.png` + `dsstore` + `.icns` files, assembled by `mozpack/dmg.py` (`create_dmg_from_staged`). The `.DS_Store` is a binary Finder-layout artifact regenerated by hand per brand (documented Mozilla procedure: build, arrange DMG in Finder, copy `.DS_Store` back into the branding dir) | HIGH | Requires a macOS packaging host. `firefox.icns`, `disk.icns`, `document*.icns`, `background.png`, `dsstore` are all branding-dir slots the generator must fill. DMG can technically be assembled on Linux via `dmg.py`, but signing (`mach macos-sign`) and verification need macOS — do the real build on macOS |
| Code signing for both platforms (Windows Authenticode + Apple `codesign`/notarization) | Unsigned installers trigger SmartScreen / Gatekeeper blocks; an uninstallable installer is not an installer. Mozilla signs via `mach macos-sign` (self-signed cert for dev, Apple Developer cert for production-like) | MEDIUM | Signing identity is per-downstream secret material — it must NEVER live in `configuration.toml` (which is committable brand data). Identity goes in the manifest; certificates stay in the build environment. v1.1 table stakes = the build accepts externally-provided signing inputs and documents them; actually holding a cert is a release-process item |
| `docs/BUILD.md` installer procedure | NEXT-MILESTONE-INPUTS explicitly calls this out as missing. The Windows requirement ("must build on a Windows machine") and the macOS dsstore ritual are non-obvious and must be written down or every downstream rediscovers them | LOW | Pure docs. Include: host requirements per platform, `mach package` invocation, signing steps, stub-installer note (see anti-features) |
| Installer verifier threading the fixture root (WR-07) | The existing installer verifier must run against fixture rebrands, not just the project's own manifest, or it proves nothing about downstreams — same "verify reads the manifest, not constants" rule as v1 | LOW-MEDIUM | Pre-fix before PKG-01 proper; small change, gates everything below |

#### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Single-manifest propagation into NSIS + DMG + MSIX surfaces | No fork documents one edit flowing into the Windows installer name, the DMG volume name, and the macOS bundle ID simultaneously. If the generator already owns `branding.nsi`/`dsstore`/bundle strings, this is nearly free and is the installer half of the single-file claim | MEDIUM | Builds directly on the Phase-3 emitter pattern (one emitter per format, parameterized by variant) |
| Per-fixture installer verification in CI (or staged for packaging hosts) | Nobody else verifies rebranded installers at all. Even "assembles on the packaging host + asserts brand strings in the produced artifact" is unclaimed territory | MEDIUM-HIGH | Full CI needs Windows/macOS runners; the staged form (build script + assert script a human runs on the host) is the v1.1-appropriate slice |

#### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Stub installer (`setup-stub.exe`) in v1.1 | "Firefox ships one, so should we" | The stub is a second NSIS build (`stub.nsi`) plus a web-rendered GUI hosted in IE's `IWebBrowser2` control via a custom NSIS plugin, with per-brand CSS/background assets. It is a large, Windows-GUI-specific surface for a download-size optimization irrelevant before there are users to download | Ship the full installer only; stub is a post-users feature |
| Maintenance Service (`maintenanceservice_installer.nsi`) | Silent updates without UAC | Requires a separately-installed elevated Windows service with its own installer, cert, and update-server trust chain. Without a live update server (which v1.1 does not have) it updates nothing | Defer until an update server exists; document as out of scope |
| MSIX packaging in v1.1 | Microsoft Store distribution | `msix/` branding slots + AppX manifest identity + Store signing is a third packaging pipeline behind the two native ones. No downstream has asked for Store distribution | Generate the `msix/` branding slots as inert files if cheap (keeps the branding dir complete); do not build or sign MSIX |
| Cross-compiling the Windows installer from Linux | Avoids needing a Windows host | Mozilla documents this as unsupported: the installer build depends on tools only available on Windows. Fighting upstream's packaging is exactly what the patch-stack discipline forbids | Windows host or Windows CI runner, documented in `docs/BUILD.md` |

### Area 2: Extensions — EXT-02 (npm + local-path sources) + WebExtensions declaration

v1 shipped EXT-01: `[[extensions]]` entries with Open VSX id or direct URL + mandatory sha256, resolved by the generator into the application `package.json`'s `theiaPlugins` block, downloaded `--packed` at build time. EXT-02 adds two source kinds; the WebExtensions declaration sibling (STATE.md pending todo) declares Gecko-side add-ons.

#### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| `npm` source kind: registry tarball resolved to a pinned version + sha256, materialized as a local `.vsix`/file the `theiaPlugins` pipeline can consume | A downstream's private or unpublished plugin lives on npm, not Open VSX. `theia download:plugins` natively understands only URL values in the `theiaPlugins` map, so the generator must do the npm resolution at generate time (registry metadata → exact tarball URL → hash) and emit something the existing download step already handles | MEDIUM | Depends on: EXT-01 `theiaPlugins`-fragment pipeline (reuse, do not fork). Pin = exact version, fail-loud without it — same rule as v1. Supply-chain note: npm resolution must be locked (treat like `yarn.lock` semantics), never floating |
| `local-path` source kind: a path inside the downstream's config dir packed into the build reproducibly | The downstream developing its own `@powerbrowser/*`-style extension needs to declare it without publishing anywhere. Theia itself supports `--plugins=local-dir:` at runtime; the build-time equivalent is copying the directory/vsix into the plugins dir | LOW-MEDIUM | Depends on: `PB_CONFIG_DIR` external-config builds (CFG-05) — the path must resolve relative to the downstream's config root, never to an absolute host path (absolute paths kill reproducibility and the Sourcerer-as-downstream proof). Hash the packed content so tampering fails the build |
| WebExtensions declaration in `configuration.toml`: id + source + pin, the Gecko sibling of `[[extensions]]` | REQUIREMENTS.md bars the curated set from the tree but STATE.md's pending todo requires the *mechanism*. Without it there is no sanctioned way to ship a content-blocker-class companion or any `distribution/`-level add-on, and downstreams will hand-drop XPIs — the exact second-file-touched failure the platform exists to prevent | MEDIUM | Two upstream mechanisms exist; pick ONE (see dependency notes): (a) `distribution/extensions/{id}.xpi` + `extensions.installDistroAddons`, or (b) `distribution/policies.json` `Extensions.Install` / `ExtensionSettings force_installed`. Both are file drops the generator can own |
| Fail-loud validation for every new source kind (unknown id, unpinned version, hash mismatch, missing local path) | v1's rule — "every extensions validation failure names the entry id" (04-02) — must extend to the new kinds or the new kinds are weaker than the old ones | LOW | Extend `verify-extension-pins.mjs` + generator `generate --self-test` cases; one self-test case per failure mode per kind |

#### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| One `[[extensions]]` list spanning Theia plugins AND WebExtensions with per-entry `side` disambiguation | A downstream declares "everything my browser ships" in one manifest section instead of learning the Theia plugin system and the Gecko add-on system separately — the same unification win as `[product] name` landing in `brand.ftl` and `applicationName` from one edit | LOW-MEDIUM | Schema design only; both emitters already exist. Risk: conflating two systems with different pin semantics — keep the entry shape explicit (`side = "theia" | "gecko"`) rather than inferring |
| `--packed` + hash-verified downloads for all kinds (already v1 behavior, extended) | Reproducible, auditable extension supply chain with no unpinned transitive auto-resolution (04-02 D-04-02-01). Most Theia adopters float on Open VSX latest | LOW | Keep; extend the pin check to npm-resolved URLs |

#### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Floating versions ("always latest Open VSX / npm") | Convenience | Non-reproducible builds + silent supply-chain mutation: a downstream's build changes when a third party publishes. v1 already decided this (no pin = build error) | Mandatory pins everywhere, including npm |
| Auto-installing the curated Sourcerer addon set in the platform tree | "Showcase a working browser" | REQUIREMENTS.md explicitly bars the set itself from the tree; the platform ships the mechanism, downstreams ship the list. Bundling a list makes Power Browser a single-product tool again (the melon→gluon→surfer failure lineage) | Mechanism in tree, lists in downstream configs, proven by Sourcerer's own config |
| Inferring extension side (Theia vs Gecko) from file inspection | "Fewer manifest keys" | Magic dispatch breaks the moment both ecosystems accept the same container (a `.xpi` vs `.vsix` today; a renamed file tomorrow). Silent misclassification installs a plugin as an add-on or vice versa | Explicit `side` key; unknown side = build error |
| Runtime extension installation from the manifest (reading `configuration.toml` at startup to fetch extensions) | "Why rebuild to add an extension?" | Same build-time-only rule as branding: a release build that fetches code from the network based on a re-readable manifest cannot be verified and can be talked into running different code than was verified | Build-time materialization only, matching `sourcererPrivilegedJs` precedent |

### Area 3: Crash-report pipeline (TEL-04)

v1 state: `--disable-crashreporter` compiles the reporter client out; `breakpad.reportURL` is blanked without `[urls].crash_report` and repointed when stated (TEL-03); the endpoint allowlist tracks the derivation. TEL-04 is everything beyond repointing the URL.

#### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| A documented decision: re-enable the reporter client or stay compiled-out | `--disable-crashreporter` means TEL-04's first question is whether there is a pipeline at all. A compiled-out reporter with a repointed URL sends nothing; keeping it out is legitimate (privacy posture) but then TEL-04 is "document the absence + keep the URL derivation" rather than a pipeline | LOW (decision) / HIGH (re-enable) | Re-enabling means un-setting the mozconfig flag, which changes the build surface (crashreporter.exe/client packaging) and needs tier-3 proof. Recommend: keep compiled-out in v1.1, build the *server* side so the URL has somewhere to point when a downstream opts in |
| Self-hosted collector endpoint accepting the Breakpad/Socorro submission protocol | The client speaks a fixed protocol: multipart/form-data HTTP POST with crash annotations + `upload_file_minidump` minidump, expecting `CrashID=<id>` (accepted) or `Discarded=<rule>` (rejected) back. Any collector must speak this; Mozilla's is Antenna (Socorro). A downstream crash URL pointing at a server that doesn't implement the protocol silently drops every report | MEDIUM | Minimal viable collector: accept POST, validate `upload_file_minidump` present, persist raw crash + minidump to disk/S3, return `CrashID=`. Full Socorro (throttler, processor, stackwalker, symbols, Elasticsearch, webapp) is NOT table stakes |
| `about:crashes` shows submitted crash IDs | The client's contract with the user: on 200 + `CrashID=`, the client records the ID locally and `about:crashes` lists it. If the collector returns anything else, reports pile up unsent. This is the acceptance test for the collector | LOW | Covered by the protocol above; test by submitting a synthetic report and reading it back |
| Crash ping vs crash report separation (telemetry crash ping ≠ Socorro report) | Mozilla has two datasets: the crash *ping* (PII-free, via the telemetry ping sender, deduplicated by UUID) and the crash *report* (full minidump, Socorro, user-consented per-report). Conflating them either leaks PII into telemetry or starves the crash DB. `[telemetry] level` (`off|crash|error|all`, default off) already models the ping side | LOW-MEDIUM | Wire `crash` level → crash pings to the downstream endpoint; keep Socorro submission behind its own per-report consent dialog. Never send minidumps to the telemetry endpoint |

#### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Minimal collector shipped as downstream-runnable code (not docs) | Every small fork leaves crash reporting pointed at Mozilla or blanked. A ~100-line collector a downstream can run is genuinely unclaimed and makes `[urls].crash_report` actually usable | MEDIUM | Must live outside the platform tree per the boundary rule? No — it is platform *tooling*, not downstream data; same status as `scripts/` |
| Symbol upload wired to the collector (symbols for the downstream's own builds) | Socorro symbolicates via `minidump-stackwalk` + symbols uploaded at build time to a symbol server. Without the downstream's symbols, their processed crashes are unsymbolicated addresses — a pipeline that produces unreadable output | MEDIUM-HIGH | Build step uploads symbols; collector knows where to fetch them. Defer full signature-generation; readable stacks are the v1.1 bar |

#### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Running full Socorro (processor + Elasticsearch + Crash Stats webapp) | "Mozilla's pipeline, self-hosted" | Socorro is a multi-service AWS deployment (collector, processor, SQS, S3, Elasticsearch, BigQuery export, webapp). Operating it dwarfs the browser project and needs none of its distinguishing output (signatures, top-crashers) before there are users crashing | Minimal collector + raw-crash storage; grow toward processing only when crash volume justifies it |
| Repointing `breakpad.reportURL` at Mozilla's `crash-stats.mozilla.org` | Zero work | Sends a downstream's users' crash data (URLs, emails, memory contents — PII-gated fields) to a third party under a different product's identity; likely a trademark/policy problem on top of a privacy one | Blank by default (current behavior); repoint only at the downstream's own collector |
| Auto-submit without per-report consent | More reports | Mozilla's model is explicit per-report consent (or explicit opt-in); silent minidump upload of potentially-PII memory contents is the fastest way to destroy a new project's trust | Keep the client dialog; `about:crashes` resubmission for failures |
| `MOZ_CRASHREPORTER_URL` env var as the configuration mechanism | Easy override | Environment-origin configuration is exactly what 03-04 rejected for identity (`project_flag()` pins origins to implied; forced configure rejects environment exports). Crash destination must come from the manifest-derived pref, not ambient environment | Manifest `[urls].crash_report` → `breakpad.reportURL` pref (already built); env override explicitly unsupported |

### Area 4: SQL-backed tabs (SQL-01, promoted from backlog 999.1)

Backlog 999.1: "Make every tab a SQL row, alongside bookmarks, sessions, and anything else that can live in SQL." The seam that already exists is `TabUriRegistry` — stable tab identity, which most browsers lack. GUI-02/GUI-05 are deferred until AFTER this lands; this area is the storage/identity layer only, no tab-strip UI.

#### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Tabs as SQL rows keyed on `TabUriRegistry` identity | The registry already gives every tab a stable, canonical URI (`view:`, `terminal:`, `settings:`, output/webview/plugin schemes) in both directions (`parseName` URI→name, `uriOf` widget→URI). That URI is the primary key the backlog analysis says other browsers don't have. One row per live tab: `{uri PK, factory, options JSON, window, index, last_accessed, pinned/hidden}` | MEDIUM | Depends on: `TabUriRegistry` asserted shape (`verify-registry-shape.mjs`) — new tab kinds that the registry can't address (`uriOf` returns `undefined`) cannot be rows; the registry stays the authority, SQL is a projection of it. Sync direction for v1.1: registry → SQL (write-through on open/close/activate), never SQL → registry |
| Bookmarks/history exposed, not rebuilt (already SQL upstream) | `places.sqlite` already stores `moz_places` (one row per URL: url, title, visit_count, typed, frecency, last_visit_date) + `moz_historyvisits` (one row per visit: timestamp, transition type) + `moz_bookmarks` (hierarchy via parent/position, fk→places). Building a parallel store duplicates the profile's ground truth and rots on schema drift | LOW | Expose via read views/query helpers against the profile `places.sqlite`. Respect the MEM/temp-table split (`moz_places_temp`/`moz_historyvisits_temp` hold unflushed rows — query the views or union both). Never write directly — use the Places API; direct writes corrupt on schema change (Mozilla's own best-practice warning) |
| Sessions ingested as read-only projection (sessionstore is compressed JSON, not SQL) | `sessionstore.jsonlz4` / `recovery.jsonlz4` (`mozLz40` + LZ4 + JSON: `{windows[].tabs[].entries[]}` with per-tab history entries, `lastAccessed`, `_closedTabs`) is the restore ground truth with its own versioned schema and multi-file fallback chain (`clean` → `recovery` → `recoveryBackup` → `cleanBackup` → upgrade backup). Converting the store TO sql risks restore-path divergence — the file that fails to parse boots an empty session | MEDIUM | Read path only in v1.1: decode (strip 8-byte header, LZ4-decompress, parse) and project windows/tabs/closed-tabs into queryable rows alongside the live-tab table. Do not replace `SessionFile` writes. Closed-tabs (`_closedTabs` with `closedAt`, `closedId`) come free with this projection and are high value |
| Private-browsing exclusion | Private windows never write to `places.sqlite` — that absence is a privacy guarantee, and sessionstore segregates accordingly. A SQL tab layer that logs private tabs breaks the guarantee the substrate makes | LOW | Rule: rows only for tabs whose URI/options resolve to non-private contexts; assert absence (a test that opens a private tab and proves no row exists). Note the project's own verification ethos: absence assertions need a proven emitter — here the emitter is the write-through hook, which the test also exercises, so the check is valid |

#### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Stable tab URIs as the row key (not numeric tab ids) | Sessionstore tabs are positional (`windows[i].tabs[j]`, `index`); every other system's tab handles are ephemeral. URI-keyed rows survive restarts, reorder, and window moves — queries like "where is my `terminal:build` tab" work across sessions. This is the payoff of the GUI-04 seam and exists nowhere else | LOW-MEDIUM | The differentiator is nearly free *because* the registry exists — v1.1's job is to not squander that by keying on something weaker |
| Closed-tab retention queryable beyond the session's undo window | Sessionstore keeps bounded `_closedTabs`; a SQL projection can retain closed-tab history (URL, title, `closedAt`) indefinitely and queryably — "what did I close Tuesday" without a history trawl | LOW | Grows out of the session-ingest projection; needs a retention policy (cap rows or age, or it grows unbounded — the 142 MB sessionstore anecdote is the warning) |
| Cross-surface queries (tabs ⋈ history ⋈ bookmarks on URL) | One query answers "which open tabs have I never bookmarked", "which bookmarks are open right now", ranked by `frecency`. Three stores, one join key (URL), zero new data collection | LOW-MEDIUM | Read-only joins across the live-tab table + places views. Theia-side query API on the `@powerbrowser/tab-uris` extension is the natural home (extension point, not a `[features]` flag — ARCHITECTURE.md Anti-Pattern 6) |

#### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Replacing sessionstore with SQLite as the restore path | "One store for everything" | Session restore is crash-recovery infrastructure with a versioned format, ordered fallback chain, and upgrade backups. Replacing the write path makes Power Browser responsible for not losing users' sessions on corrupt writes — Mozilla debugs that path full-time. A v1.1 rewrite risks the worst possible failure (empty session on upgrade) | SQL as a read projection; sessionstore remains the sole restore authority. Revisit only with a dual-write + restore-parity proof, post-GUI |
| Writing directly to `places.sqlite` (SQL INSERTs for bookmarks/visits) | Faster than the Places API | Mozilla explicitly warns add-ons off direct writes: schema changes turn them into corruption. The `syncStatus`/`syncChangeCounter` columns show how much write-side invariant lives outside the visible schema | All writes via the Places API / existing services; SQL layer reads |
| A `[features]` manifest flag for SQL tabs (or per-downstream schema toggles) | "Make it configurable" | Backlog 999.1's own boundary note (ARCHITECTURE.md Anti-Pattern 6): if a downstream needs different platform behavior, the platform needs an extension point, not a flag. A flag that changes storage semantics per downstream forks every query consumer | Platform extension point (query API on the tab-uris extension); schema is platform-fixed, identical for every downstream |
| GUI tab-strip work smuggled in ("while we're here, render the rows") | Tabs-as-rows invites rendering them | GUI-02/GUI-05 are deferred until after SQL tabs by explicit 2026-09-04 scoping. Rendering needs `<xul:browser>`-backed web tabs (GUI-02) which don't exist yet; a strip over view-only URIs would be throwaway UI | Land storage + identity + query API; GUI consumes it next milestone |
| Unbounded retention ("keep every tab forever") | Queryable history is addictive | Session data (full entry history, form data, scroll position per tab) is heavy — real sessionstores reach 100+ MB. An ever-growing SQL table degrades startup and disk without a policy | Bounded retention from day one: cap closed-tab rows by count and age, document the policy, verify the prune path |

### Dependency Notes

- **PKG-01 requires the rename slice first or with it.** Every installer surface (InstallDir, DMG volume name, bundle ID, version keys) embeds the display/identity names; verifying installers under the old spaced form then re-pinning doubles the packaging-host work. Fold NAME-01 in, per scoping.
- **WR-04 + WR-07 are pre-fixes, not stretch goals.** An installer verifier that can't run against fixtures (WR-07) or that lets unexpanded variables through (WR-04) invalidates every PKG-01 result built on it.
- **EXT-02 reuses the EXT-01 fragment pipeline; it does not fork it.** The generator's `theiaPlugins`-fragment → copy-over → `verify-extension-pins.mjs` chain already handles URL entries end to end. npm must resolve *into* a URL the chain handles; local-path must pack *into* content the chain hashes. Two entry paths, one chain.
- **WebExtensions needs a mechanism decision before schema work.** `distribution/extensions/{id}.xpi` (distro-addon path, needs `extensions.installDistroAddons` understanding) vs `policies.json` `ExtensionSettings force_installed` (Chrome-parity policy, `install_url` + auto-update on version change, `file:///` URLs for local). Recommendation: `policies.json` `ExtensionSettings` — it is the policy Mozilla is actively improving ("all future improvements will be applied to that policy"), supports force-install + lockdown + update semantics declaratively, and the generator already owns pref/policy-shaped emission. Either way the curated list stays out of the tree.
- **TEL-04's load-bearing decision is keeping the client compiled out.** With `--disable-crashreporter` set, there is no client to feed; the v1.1 pipeline is therefore the *server* side (minimal Antenna-protocol collector) plus the consent/ping separation, staged so a future milestone can flip the build flag with somewhere for reports to land.
- **SQL-01's direction is registry → SQL, never reverse, in v1.1.** The registry is the authority (asserted shape, cross-checked discovery); SQL is a projection. Anything that writes tab state back (restore, reopen) waits for GUI-02, which is the consumer that justifies it.
- **Places and sessionstore are expose/ingest, never replace.** Both have upstream-owned schemas, invariants invisible in the DDL (`syncStatus` counters, session fallback chain), and corruption failure modes. The new schema is only the live-tab table — the one layer where no upstream store exists.

- [ ] **NAME-01 rename slice folded into installer work** — `identity.display_name` → `PowerBrowser`, gates re-pinned, propagation proof re-run
