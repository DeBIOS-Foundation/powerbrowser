Detector signal: `pluralization` ("a mode's second visit" in the phase goal). Read against the scope, the real generalization this phase introduces is a SECOND tab kind whose address is not a Theia-minted `scheme:name` but a page URL, and a second destination for "+" (in-shell web tab alongside the GUI-01 stock window).

- Noun that is primary: the tab's **address** — the `TabUriRegistry` URI. It was already the generalized identity (GUI-04 bridge interface: every tab has a URI); web tabs join it as one more `uriOf` branch whose URI is the page URL.
- Decision: **no-change** to the identity model. The registry URI stays primary; `WebTabWidget.url` is the variant's source of that URI, read live. The per-session counter is a construction-option discriminator and never part of identity (docs/URI-SCHEMES.md general rule).
- Accepted debt (add-alongside, recorded): the store row is keyed by page URL, so two web tabs on one URL share one row and closing either removes it (UI-SPEC A18, the stock `webview:` ceiling). What would force a promote: a requirement to distinguish two tabs on one URL in Panorama or setups — that needs a stable per-tab key in the store schema, out of scope this milestone. Marked with a `ponytail:` comment at the row-write site in plan 01.
- Invariant test (accepted, already planned): plan 03's live check asserts `uriOf(webTab).toString(true)` equals the overlay's live URL after navigation — the assertion goes red the moment a future change reintroduces the "URI comes from construction options" assumption.
</assumption_delta_decision>
