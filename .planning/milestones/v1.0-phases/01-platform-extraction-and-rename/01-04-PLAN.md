<objective>
Complete the walking skeleton: re-derive both patches so the 3-way-merge chain is valid, fetch
`upstream/` with the script, apply, build, launch, and prove on the built artifact that the
application is Power-Browser-branded and reaches nothing it should not.

Purpose: this is the far end of the stack and the phase's expensive step. A full `./mach build` is
unavoidable — the product identity values are compiled defines and the XPCOM manifest is a tier-3
build trigger, so artifact builds cannot produce a renamed binary — and it measured roughly forty
minutes on this host with a sccache hit rate near zero on exactly this kind of change. Everything
cheap that could catch a mistake has already run in plans 01-01 through 01-03; this plan spends the
forty minutes once.

Output: a working `objdir/dist/bin/powerbrowser`, both patches regenerated with a valid hash chain,
and every runtime verifier green against the built binary.

Never text-edit a patch to change its content. Editing the body without recomputing the `index` blob
hashes leaves a patch whose 3-way merge cannot resolve, which degrades the applier into the silent
no-op mode it exists to catch. Plan 01-02 rewrote the patch bodies' brand literals; this task
re-derives both files properly so the hashes match again.

Procedure:

1. `rm -rf upstream` then `scripts/fetch-upstream.sh`. This is the MIG-01 proof — the tree comes from
   a script-driven shallow clone at the pinned ESR tag, never from a copy. Confirm the script created
   the symlink into the renamed tree and appended the matching git-exclude line, because both name the
   tree and both were renamed. A fresh clone starts with a clean exclude file, which is why the
   sequence is rename first, fetch second; if a stale `upstream/` were present the remediation the
   scripts themselves recommend is to remove it entirely.
2. Apply the intended edits directly to the two upstream files. In `browser/moz.configure`: the vendor
   implication takes `DeBIOS`, the UA-name implication stays `Firefox` and the app-id implication stays
   Firefox's, both frozen for extension compatibility; the browser-chrome-URL implication points at the
   renamed chrome package's shell document. In `browser/moz.build`: the directory list gains the
   relative path to the renamed shell tree, with the existing comment block carried forward verbatim
   including its historical decision-ID citations.
3. Re-derive each file's diff with `git -C upstream diff` per path, then split by hunk into the two
   patch files along the existing split: identity hunks into `010`, shell hunks into `020`.
4. Assert the chain by reading the `index` lines: for the file both patches touch, the identity
   patch's post-image hash must be exactly the shell patch's pre-image hash. This is a literal
   equality between two strings in two files; if it does not hold, the split was wrong.
5. Prove it end-to-end: `rm -rf upstream`, `scripts/fetch-upstream.sh`, `scripts/apply-patches.sh` —
   which must report both patches applied and verified non-vacuous. Run the applier a second time; it
   must FAIL and name the patch, which is the silent-no-op guard firing. Then run
   `scripts/check-patch-surface.sh`.
6. Run `scripts/fetch-upstream.sh --self-test` and `scripts/apply-patches.sh --self-test`. Neither
   script's logic is rewritten in this phase — they are the accumulated encoding of failure modes this
   project already hit once, and their job here is to still work under new names.

Do not add, remove, or reorder hunks beyond what the rename requires. Stripping brand values out of
the patches into generated includes is Phase 5's work and depends on a generator that does not exist
yet.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network → `upstream/` | A shallow clone of a third-party repository at a pinned tag is executed as build input. |
| patch stack → Gecko source | Two patches mutate upstream build files. A patch that applies to nothing is indistinguishable from one that applied, absent an assertion. |
| launched browser → the internet | An unattended launch may reach hosts the product never declared. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | `git apply --3way` silent no-op | high | mitigate | Re-derive both patches from a patched tree so the `index` blob hashes are real; assert the chain by string equality; require the applier to report non-vacuous on a clean tree and to FAIL by patch name on a second apply. Never text-edit a patch body. |
| T-04-02 | Tampering | patch touching a compiled Gecko path | high | mitigate | `scripts/check-patch-surface.sh` reads targets from the `+++ b/` headers only and checks them against a suffix set transcribed from the mozbuild emitter. Run it after every regeneration. |
| T-04-03 | Tampering | upstream clone integrity | medium | mitigate | Clone at a named release tag from the canonical Mozilla repository and assert `git describe --tags` matches the pin. `upstream/` is gitignored so nothing about it is ever committed. |
| T-04-04 | Elevation of Privilege | backend auth gate after the rename | high | mitigate | The smoke script sets the test bypass and therefore cannot prove the gate. Task 2 adds two positive controls — unauthenticated rejected, minted token accepted — registered as labelled checks. |
| T-04-05 | Information Disclosure | unattended network callout from the launched build | high | mitigate | `scripts/verify-endpoints.sh` runs against the built artifact with a fail-closed allowlist: a host observed at runtime and absent from the allowlist is a failure, not a silent pass. |
| T-04-06 | Spoofing | branding verifier reading the manifest instead of the artifact | high | mitigate | The identity verifier reads `objdir/dist/bin/` and never the sources. Its positive-control mode is run alongside the real check so a comparison that agrees with everything is caught. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | The `yarn install` in Task 2 resolves only already-pinned packages against a committed lockfile; no new dependency is introduced. The one net-new dependency in this phase is gated by a blocking human checkpoint in plan 01-06. |
