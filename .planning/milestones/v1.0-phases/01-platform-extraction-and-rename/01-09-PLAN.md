**Step 1 — the log analyzer (`--log <path>` mode) in `scripts/verify-start-path-recovery.mjs`.**
Give the script the same shape `scripts/verify-shell-error-copy.mjs` uses: a `failures` array, a
`fail()` helper, per-mode functions, and a final PASS/FAIL print with `process.exit`. Resolve the
repo root from `import.meta.url` exactly as that script does. Accept `--log <path>`, `--file
<path>`, `--shell-file <path>` and `--self-test`, and reject any unknown argument with a named
failure.

Before matching anything in a log, the analyzer must prove the sentinel prefixes it greps for are
emitted by the code under test rather than by its own expectation. Read the chrome bootstrap file
(default `powerbrowser/shell/powerbrowser.js`, overridable with `--shell-file`), collect the set of
sentinel prefixes it passes to `dump(`, and fail by name if either the swap sentinel prefix or the
deck-state sentinel prefix is absent from that set. That check is what makes a later rename of
either sentinel go red here instead of silently never matching.

Derive the health-gate failure's log signature the same way rather than hand-keeping it: read the
supervisor source (default `powerbrowser/shell/TheiaService.sys.mjs`, overridable with `--file`),
locate the `_fatal(` call that reports the health probe never returning 200, and build the match
pattern from that template's fixed leading text. Fail by name if that call site cannot be located,
because a template that moved makes every log assertion below vacuous.

With those two derivations in hand, assert over the log, tolerating the
`[PowerBrowserAPI] <level>: ` mirror prefix the harness's own `first_byte_offset` tolerates:
  - the derived health-gate failure line is present — the planted fault actually fired;
  - the swap sentinel is present;
  - the swap sentinel appears exactly once — the one-time block ran once, not twice;
  - the deck-state line whose `where` field is the swap reports `loading` as `none` — parse the
    JSON payload, do not substring-match the whole line;
  - the first occurrence of the derived failure line precedes the first occurrence of the swap
    sentinel, by byte offset. Without this ordering assertion the check would also pass on a run
    where the first health probe simply succeeded, which is the happy path the existing smoke
    tests already cover and the exact vacuity this gap exists to remove.

**Step 2 — `check_health_gate_recovery_swaps` in `scripts/verify-platform.sh`.** Model it on
`check_shell03_auto_dismiss_on_selfheal`. Build under `mktemp -d` (registered with `track_temp`, as
every fixture in that file is — never a persisted repo file) a wrapper backend entry file plus a
marker file initialised to 0. The wrapper increments the marker on every invocation, parses its own
`--port` argument out of `process.argv`, and then:
  - on invocation 1, starts an HTTP server bound explicitly to `127.0.0.1` on that port which
    answers every request with status 503, prints the readiness sentinel line carrying the bound
    port and its own pid as JSON, and stays alive. This is the plant: readiness announces (so the
    supervisor pins the port), the health gate cannot pass, and the output stream never ends — so
    the failure classifies as the health-probe timeout the gap describes and not as a crash;
  - on invocation 2 and later, starts an HTTP server bound explicitly to `127.0.0.1` on that port
    which answers 200, prints the same readiness sentinel, and stays alive.
Bind host `127.0.0.1` explicitly on both branches: a fixture that answers 200 to everything must
never be reachable off-host.
