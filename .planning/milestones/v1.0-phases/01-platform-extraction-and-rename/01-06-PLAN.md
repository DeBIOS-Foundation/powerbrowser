<objective>
Make web pages openable inside Theia as URL-addressable tabs (GUI-02), and assert the tab-URI
registry's exported shape so the future unified tab strip stays landable (GUI-04).

Purpose: per D-19 this is net-new work, not migration. Research established that it does not exist in
the source tree — the URI registry covers seven internal schemes and there is no http or https handler
anywhere in the Theia workspace, and no bridge package exists despite prose references to one. It also established the one real limitation: an iframe-rendered
web tab cannot display an origin that refuses framing, which includes most large sites. That
limitation is designed around with an always-visible escape rather than detected, because a blank
iframe fires no reliable error event and any detection is a timeout heuristic that misfires on slow
pages. Sites that refuse framing are exactly what plan 01-05's real browser window is for; the two
requirements complement each other and the code should say so.

Output: a pinned first-party widget dependency, an http and https open handler, an always-visible
escape action, a fifth documented carve-out, a new round-trip row, and a registry-shape assertion.
</objective>

  <action>
**Install.** Add the widget package to the tab-uris extension's dependencies at exactly the same
version string as the eight framework packages already pinned there, and add the identical pin to the
workspace resolutions block alongside the other 49. Both are required — a pin in only one place lets
the workspace resolve a mismatched framework core. Run the install inside the theia devShell and
commit the updated lockfile.

**Read before writing.** Open the installed package's own browser sources and determine the real
factory identifier and the real shape of the options object the widget factory takes. Research
recorded these as an explicit unverified assumption precisely because the package was not installed
when the research ran. Write the handler against what the source says.

**The handler.** Add a new module in the tab-uris extension implementing the plain open-handler
interface. Its id follows the extension's convention of a platform-scoped, scheme-named handler id.
Its scheme predicate answers synchronously on the scheme alone: a fixed priority for the http and
https schemes and zero for everything else. Everything else explicitly includes the script scheme, the
data scheme, and the local-file scheme — an arbitrary user-supplied URL entering an iframe is a new
input surface, and the scheme is validated before any widget is constructed rather than after.

Its open path resolves the widget through the widget manager keyed on the URI, so the same URL
round-trips to the same tab, which is what makes it URL-addressable. Attach to the main area only if
not already attached, then activate, then return the widget — the same sequence the analog uses. Any
error thrown is prefixed with the handler id and states what the user should do instead.

**The escape action.** Every web tab carries an always-visible action that hands the tab's current URL
to the browser-window command exported by plan 01-05, invoking it by the exported id constant rather
than by a duplicated string. Its label is the one the UI design contract fixes. It is always visible,
never conditional on a detected error: an origin refusing framing renders a blank iframe and fires no
reliable error event, so any detection is a timeout heuristic that will misfire on slow pages. A
persistent escape is less code, never wrong, and gives a user staring at a blank tab a working next
step with no detection at all.

**Binding.** Bind the handler to itself in singleton scope and then to the open-handler service, as a
static binding at module load alongside the existing handler bindings, for the same reason those are
static — the contribution provider caches on its first lookup, so late registration is an escape
hatch, not the ordinary path.

**Presentation.** The widget's loading state, error state, and empty state are the stock widget's own.
Author no replacements and add no custom widget chrome. Add no font-size, font-family, font-weight, or
colour literal anywhere in this extension — Theia-side presentation is delegated to its own theme
variables, and a hardcoded value defeats the customize bridge a downstream restyles through.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-supplied URL → iframe widget | An arbitrary URL entering a framed widget is a new untrusted-input surface this phase creates. |
| framed remote page → Theia frontend | The Theia frontend publishes its dependency-injection container on a global in every build; a hostile framed page is adjacent to it. |
| npm registry → the workspace | One net-new third-party package enters the dependency tree. |
