<objective>
Close the two user-facing gaps a mechanical rename would carry forward — internal identifiers leaking
into full-screen error text, and three buttons with no keyboard focus indicator — write this repo's
own project-instruction file, and run the phase gate.

Purpose: a pure rename would prefix the leak with a new product name and ship it, and the error deck
is exactly the state a user reaches when the pointer-driven happy path has already failed, so a
keyboard user with no visible focus ring is stranded there. Both are cheap and both become someone
else's problem if deferred. The instruction file matters for a different reason: the source tree's
fifth hard rule states that the sidecar is the only GUI and no browser chrome exists, which directly
contradicts the requirement this phase just delivered. Copying it verbatim would encode a constraint
against our own product.

Output: rewritten error copy with a complete diagnostics surface, a focus indicator, `CLAUDE.md`, the
debranded documentation, and a green full-suite phase gate.
</objective>

Rewrite the eight user-facing failure strings to the exact copy the design contract's rewrite table
specifies, and move every dropped identifier into the diagnostics surface. Keep this as its own
commit after the rename stages so the rename diff stays purely mechanical and bisectable; this is a
behaviour change, deliberately separated.

The three rules the contract fixes, applied to every string: name the product as `Power Browser`;
state the problem in plain language a non-developer understands; end with a next step that is a real
affordance visible on screen, which here is either the retry control or the details control. Several
distinct failure paths collapse to the same user-facing sentence — that is intended, because the
distinction between them is diagnostic, not actionable, and the diagnostics layer is what exists for
the distinction.

Every identifier the rewrite drops from the message becomes a diagnostics field row: the preference
key that was unset or unresolvable, the resolved path that did not exist, the readiness sentinel that
never arrived, the port the health probe used, the timeout that elapsed, and the raw exception text.
Nothing is lost — it moves from a full-screen string a user cannot act on to a labelled row in the
layer that exists to carry exactly that. Field rows render only for identifiers present on the current
failure; an absent identifier produces no empty-labelled row.

The shutdown message is not an error surface and stays verbatim.

Any assertion in a smoke or verification script that matches one of the old literals must be updated
in this same commit, or the script starts matching nothing and passes vacuously.

Add a labelled check to the consolidated verifier asserting that no string written to the error
element matches an internal-identifier shape — an all-caps underscored token of four or more
characters, or a dotted multi-segment preference key. Assert by pattern rather than by a list of
banned literals, so the check keeps working when a future failure path is added.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internal failure detail → full-screen user surface | Diagnostic identifiers written into user-facing text disclose internal structure to anyone looking at the screen. |
| runtime stylesheet and privileged script → the shell | The customize bridge intentionally lets a user's own file change the running product. The development-flagged script half is the privileged one. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Information Disclosure | full-screen error text | medium | mitigate | Internal identifiers move out of the user-facing message and into the diagnostics layer, which is reached deliberately. A pattern-based labelled check prevents a future failure path from reintroducing the leak. |
| T-07-02 | Elevation of Privilege | development-flagged privileged script | high | mitigate | The existing flag-off verifier asserts the privileged binding is absent when the development flag is off; it is run at the gate and is registered as a labelled check. The flag must stay off in release. |
| T-07-03 | Tampering | runtime stylesheet layer | low | accept | Letting a user's stylesheet restyle the shell is the requirement, not a defect. Bounded by the shell document's content-security policy, which drops anything that is not a chrome-scheme resource. Accepted. |
| T-07-04 | Spoofing | verification passing vacuously after the copy rewrite | high | mitigate | Any smoke or verification assertion matching an old error literal is updated in the same commit; a stale matcher matches nothing and passes silently. `scripts/smoke-firefox.sh` is re-run as an acceptance criterion specifically to catch this. |
| T-07-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan. |
</threat_model>
