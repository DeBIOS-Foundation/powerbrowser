# Phase 4 Plan 01 — Tracer: one branding key end-to-end + runtime channel

**Goal:** Carry a single Theia branding value (`identity.display_name`) from
`configuration.toml` through schema, generator, and frontend config to the
running welcome widget WITHOUT editing any `theia/**/src/**/*.ts` branding
literal, and ratify the runtime channel every later Phase 4 plan uses.
Proves the GEN-05 mechanism on one key before the full surface follows.

**Requirements covered:** GEN-05 (partial — tracer slice only)

**Wave:** 1 (no dependencies; all later Phase 4 plans block on this one —
shared `scripts/generate.mjs` + `scripts/lib/config-schema.json` force
sequencing, same as Phase 3)

## Tasks

### Task 1 — Spike and ratify the runtime branding channel (no new emitter yet)

1. Read `theia/node_modules/@theia/application-package/src/application-props.ts`
   (`FrontendApplicationConfig`: `applicationName`, `defaultTheme` — injected
   into `index.html` at `theia build` time from the application
   `package.json`'s `theia.frontend.config`) and confirm: (a) changing those
   two keys requires only the app-bundle step (`yarn --cwd
   theia/applications/browser build`), NOT `tsc -b` in any extension;
   (b) there is NO frontend-config key for welcome text, about text, logo, or
   repo URL — those need a second channel.
2. Spike the second channel with a throwaway (not committed): generator writes
   a JSON file, the welcome widget fetches it at runtime. Candidate location:
   a static asset served by the Theia backend (check how `src-gen/` or the
   app's static dir is served; `token-gate` backend contribution shows the
   backend-extension pattern). Alternative candidate: backend
   `ApplicationServer` extension serving branding info. Pick whichever needs
   no `src/**/*.ts` edit per rebrand and no new backend module beyond one
   file in a `@powerbrowser/*` extension (hard rule: never fork/patch Theia
   core; GUI-02 D-22 gate precedent — a second backend module needs
   justification, prefer a static asset if servable).
3. Record the decision (channel + file paths + why) in the plan SUMMARY for
   04-02..04-04 to build on. If NEITHER channel works without a `.ts` edit
   per rebrand, STOP and return `## PHASE SPLIT RECOMMENDED` — do not invent
   a fake channel.

**Verify:** `git status --porcelain theia/` shows zero modified `src/**/*.ts`
after pointing the spike at a fixture value and re-running only the app
bundle step; welcome tab shows the fixture value. (Honest check: it reads
the live widget, not a config dump.)

### Task 2 — Schema + emitter: `applicationName` from the manifest

1. `scripts/lib/config-schema.json`: NO new key needed for the tracer
   (`identity.display_name` already required). If the Task 1 channel needs
   new `[theia]` keys (e.g. `theia.welcome_text`), add them here now with
   `required: false`, `type: string`, and a `regex` + `regex_help` +
   `regex_example` in the established style — cosmetic keys default with
   echo (CFG-04), never silent fallback.
2. `scripts/generate.mjs`: add a TARGETS row emitting the application
   frontend config (`applicationName` = `identity.display_name`) in the
   established `{generated, tracked?, variant, emit}` shape. Follow the
   Phase 2 copy-over precedent for the tracked application
   `package.json`: emit the `theia.frontend.config` block to
   `generated/theia-frontend-config.json` and surgically apply ONLY that
   block to `theia/applications/browser/package.json` (whole-file
   byte-identity is brittle — yarn rewrites that file; assert block-level
   equality instead, everything else byte-identical). New emitter obeys the
   file's header rules: sink guards on every interpolated value
   (`assertEmittable`), literal `\n` joins, no reformat/tidy.
3. `generate --self-test` FIXTURE_BASE: add any new key used, so fixtures
   still pass validation (a fixture failing validation makes every
   planted-fault case red for the wrong reason). Add one planted-fault
   self-test case: manifest with the display name carrying a sink-guard
   character must fail naming the dotted path.

**Verify:** `node scripts/generate.mjs --self-test` green;
`node scripts/generate.mjs && git diff --stat` shows the application
`package.json` frontend block updated and nothing else outside `generated/`.

### Task 3 — Extension reads runtime value; preflight + registry follow

1. `theia/extensions/branding/src/browser/powerbrowser-welcome-widget.tsx`
   (and ONLY the read site — one file): resolve the display name at runtime
   through the Task 1 channel (`FrontendApplicationConfigProvider` /
   `ApplicationProps` for `applicationName`; Task 1 channel for the rest),
   keeping the hard-coded `'Power Browser'` as the fallback when the runtime
   value is absent (tree must still boot pre-generator). Same-file change
   only — about dialog, favicon, mark stay literal until 04-04.
2. `scripts/verify-branding-preflight.mjs`: update ONLY the welcome-widget
   section touched by (1) — expectations stay derived from
   `inventory/brand-tokens.json`'s `brand_display_expectations` (the schema
   file's `$comment` forbids reading the manifest as expectation source:
   same-pass input vs output always agrees with itself). Keep the
   sources-clean half real: assert the read site carries no display literal.
   Add/adjust `--self-test` planted-fault rows so each goes red naming the
   drift (CLAUDE.md rule: every check needs a `--self-test` proving red).
3. `scripts/verify-platform.sh`: register the new/changed label(s) in the
   `--quick` table (label|command form, alongside the existing
   `branding-preflight` rows). Do NOT create a sibling driver.

**Verify:** `scripts/verify-platform.sh --quick` green;
`scripts/verify-branding-preflight.mjs --self-test` green (each planted
fault observed red); rebrand drill: fixture `display_name = "Acme Browser"`
→ generate → app-bundle-only rebuild → welcome shows "Acme Browser" with
`git status` showing zero modified `theia/**/src/**/*.ts`.
