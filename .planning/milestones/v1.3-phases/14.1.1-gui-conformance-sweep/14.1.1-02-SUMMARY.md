## Decisions Made

- **The thumbnail is read back through `GroupQueryService.getThumbnail`, not `ChromeBarSuggestionService.searchByPrefix`.** The plan said to reuse "the same backend reader the store phase already uses", but the suggestion row projection drops the `thumbnail` column, so that reader could never have seen one. `GroupQueryService` is the same backend handle (`TabQueryService`) one RPC method over, and it is the reader Panorama itself uses — so the phase reads the row through the same path the card does.
- **`channel.send`, never `channel.request`, for the phase's hide.** The `lost-view-ignored` plant deliberately makes a geometry request never resolve. A phase that awaited that reply hung the whole session at the BiDi timeout instead of letting the plant go red on its own assertion. Nothing in the phase needs the reply — the evidence is the stored row.
- **`thumb-not-scheduled` is labelled an assertion test in its own comment.** The schedule and the capture are both chrome-side; every plant runs in the page realm, so no reachable seam removes the schedule. The plant strips the *read*, which proves the thumbnail assertions are reachable and independent of the row assertions — it does not prove the capture path filled them. What proves that is the recorded pre-fix RED. Saying so in the comment was preferred to a plant that looks stronger than it is.
- **`closeStockTabByUri` was deliberately not repointed.** It dereferences `found.tab`, which is `null` for an overlay. The reason is written at both lookups so a later reader cannot "unify" them into a crash.
- **The `dropdownAfterEnter` phase types an upper-case scheme.** Typing the value the pill already shows leaves React's change tracker unchanged, so no `onChange` fires, nothing arms the bar and no query is ever scheduled to outrun — the phase would have been silently vacuous. Chrome canonicalises the upper-case scheme back to the same page, so no later phase is disturbed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The reader the plan named cannot see a thumbnail**

- **Found during:** Task 1
- **Issue:** The plan says to "read the row back through the same backend reader the store phase already uses" — `ChromeBarSuggestionService.searchByPrefix`. Its row projection has no `thumbnail` field (`chrome-bar-suggestion-service.ts`), so that reader returns a row whose thumbnail is structurally absent whatever the capture did. The assertion would have been red forever, including after a correct fix.
- **Fix:** Read through `GroupQueryService.getThumbnail(uri)`, reached through the same `__getByName` DI walk, wrapped on the probe as `P.thumbnailOf` so the plant has one seam. This is the same backend handle and the reader Panorama's own cards use.
- **Files modified:** `scripts/verify-web-tab-live.mjs`
- **Verification:** RED run returned `undefined` (reader working, row empty); GREEN run returned an 918-char PNG data URL
- **Committed in:** `6311c2d`

**2. [Rule 1 - Bug] The new phase hung the `lost-view-ignored` plant's session**

- **Found during:** Task 1 (first `--self-test` run)
- **Issue:** The thumbnail phase hid the overlay with `await P.channel.request({ kind: 'webTabGeometry', ... })`. The `lost-view-ignored` plant replaces `channel.request` so geometry messages return a promise that never settles — legitimately, that *is* the pre-fix behaviour it restores. The awaited hide therefore never returned and the whole session died on `BiDi request 'script.evaluate' timed out after 20000ms`, taking a previously-green plant with it.
- **Fix:** Use `channel.send` for the hide and drop the reply diagnostic. The reason is written at the call site so it is not "simplified" back to `request`.
- **Files modified:** `scripts/verify-web-tab-live.mjs`
- **Verification:** re-run `--self-test` — `lost-view-ignored` back to red naming `lost-view`, all ten plants red, clean control green
- **Committed in:** `6311c2d`
