### CR-01: The per-dialog walk cannot see a `msg:` that is a raw literal or a bare constant — uncontracted dialog body copy passes green

**File:** `scripts/verify-gui09-setups-copy.mjs:240-247` (paint site 3, `msg` resolution);
claim falsified at `:39-43` (header) and `:487` (PASS line); plants that miss it at `:627-637`
(plant 9) and `:646-665` (plant 10)

**Issue:** Paint site 3 reads `title`, `ok` and `cancel` as string literals but reads `msg` with

```js
const msg = dialog.body.match(/\bmsg\s*:\s*(\w+)\(/);
if (msg) { /* template or unresolved */ }
```

The pattern requires an identifier followed by `(`. When `msg:` is anything else the `if` is
simply skipped — nothing is pushed to `copy` and nothing to `unresolved`. Two forms a real
second dialog would take are therefore invisible: a raw literal (`msg: 'Everything you saved will
be wiped.'`) and a bare identifier naming an exported constant that has no Copywriting Contract
row (`msg: WIPE_BODY`). Paint site 5 handles exactly this asymmetry correctly (`:261-270`: a
non-identifier argument is `unresolved` and red); paint site 3 does not.

Reproduced in a scratch copy of the three input files (repo untouched; the scratch control run
matched the real gate's PASS line byte for byte). Inserting after the real dialog's `addClass`
line a second dialog with contracted `title`/`ok`/`cancel`, the danger class, and

- variant A — `msg: 'Everything you saved will be wiped and cannot be recovered.'` →
  `verify-gui09-setups-copy: PASS -- 18 painted setups strings ... 2 ConfirmDialog
  construction(s) each with a danger-scoped class ("dialog" carries ...; "second" carries ...)`,
  exit 0;
- variant B — `msg: WIPE_BODY` with `export const WIPE_BODY = 'Everything you saved will be
  wiped.';` added to the service → same PASS line, exit 0.

A control (variant C: the *first* dialog's `msg` replaced by a raw literal) goes red, but only as
`dropped contract` for the template it displaced — the raw literal itself, which in that variant
carried `powerbrowser.setups.delete`, is still never scanned by `internalsOf`. So an internal
identifier inside a dialog body is not caught by the no-internals half either.

Plants 9 and 10 both write `msg: setupDeleteBody(row.name)`, so the self-test exercises only the
one `msg:` form the deriver handles. The header's statement that since 14.1.1-12 the gate "reads
each one's own object literal" and that "a second dialog's copy ... [is] red (self-test plant 9)"
is true for three of the four fields.

**Fix:** Resolve `msg` with the same four-way dispatch paint site 1 uses for a flash argument,
and make anything else unresolved:

```js
const msg = dialog.body.match(/\bmsg\s*:\s*([^,\n]+?)\s*,/);
if (msg) {
    const arg = msg[1].trim();
    const call = arg.match(/^(\w+)\(.*\)$/);
    if (call) {
        if (templates.has(call[1])) { copy.push(templates.get(call[1])); } else { unresolved.push(call[1]); }
    } else if (/^\w+$/.test(arg)) {
        resolveIdent(arg);
    } else if (/^'((?:[^'\\]|\\.)*)'$/.test(arg)) {
        copy.push(unescapeLiteral(arg.slice(1, -1)));
    } else {
        unresolved.push(arg);
    }
} else {
    unresolved.push(`ConfirmDialog bound to "${dialog.binding}" has no msg field`);
}
```

Then add plant 11: a second dialog identical to plant 10's but with
`msg: 'Everything you saved will be wiped.'`, required to go red naming that literal as
`unreviewed copy`; and plant 12: `msg: WIPE_BODY` with the constant exported and uncontracted,
same red. Correct the header sentence to name all four fields once the plants exist, in a later
commit than the plants (the discipline `14.1.1-UAT.md:968` records).

### WR-01: Folding `refused-scheme` at the navigate site marks a live overlay as lost and gives a Reload that can never succeed

**File:** `theia/extensions/tab-uris/src/browser/web-tab.ts:352-354` (`lostReply`), `:470-477`
(`navigate`), `:536-539` (`settle`), `:514-533` (`reopen`); chrome semantics at
`powerbrowser/shell/PowerBrowserAPI.sys.mjs:2320-2324` (`webTabNavigate`) and `:2163-2170`
(`webTabOpen`)

**Issue:** Commit `e3e0f92` added `reply.where === REFUSED_SCHEME_OUTCOME` to `lostReply()`.
That predicate is correct for an *open* (chrome created nothing, so nothing renders) but it now
also serves `settle()`, which folds every `webTabNavigate` reply. Chrome refuses a navigate
**before** touching the overlay:

```js
webTabNavigate(tabId, url) {
    if (spec !== "about:blank" && !/^https?:\/\//i.test(spec)) { return "refused-scheme"; }   // :2322-2323
    const entry = webTabs.get(tabId);                                                          // :2325
```

so after a refused navigate the previous page is still rendering in the overlay. The widget's
state after `navigate()` is then inconsistent three ways: (a) `this.url` was overwritten at `:471`
before the reply arrived, so the strip label, caption and `aria-label` name the refused URL while
the overlay shows the old page; (b) `lostView` is `true` and `LOST_VIEW_COPY` is painted into the
placeholder, but `publish()` still sends `visible: true` (`hasPage` is true), so the live overlay
occludes the copy the user is being told to act on; (c) the copy's next step is "Choose Reload to
try again", and Reload routes to `reopen()` → `webTabOpen(tabId, refusedUrl)` → `refused-scheme`
again, because the scheme check at `:2165` precedes the `already-open` check at `:2168`. The
affordance the contract names cannot succeed from this state.

Reachability today: none through the shipped callers. The only `navigate()` caller,
`chrome-bar-widget.tsx:291-297`, is reached only from `openCommittedUrl` behind the same
`^https?:\/\//i` test chrome applies (`:274`), so the arm is currently dead at this site. It is
latent, not live — but it was introduced by pass 3 at a site pass 2 did not analyse, and a second
caller of the public `navigate()` (Panorama, a link handler) would hit it.

**Fix:** Treat a refused navigate as a no-op that rolls back, without adding a second
`setLostView` reading (which the bridge gate would correctly refuse):

```ts
async navigate(url: string): Promise<WebTabReply> {
    const previous = this.url;
    this.url = url;
    this.refreshTitle();
    this.renderState();
    this.publish();
    const reply = await this.channel.request({ kind: 'webTabNavigate', tabId: this.tabId, url });
    if (reply.ok === true && reply.where === REFUSED_SCHEME_OUTCOME) {
        // Chrome declined before touching the overlay: the previous page still renders.
        this.url = previous;
        this.refreshTitle();
        this.renderState();
        this.publish();
        return reply;
    }
    return this.settle(reply);
}
```

`lostReply()` keeps its third arm (it is right for `onAfterAttach` and `reopen`), so block 8 of
the bridge gate stays green. Record the reasoning beside `publish()`'s existing exception at
`:426-432`, which is the same shape: one documented site where the shared predicate is
deliberately not the whole story.

### WR-02: The broken-instrument scorer filter is new logic with no fixture, matched by a hand-spelled literal at five sites

**File:** `scripts/verify-web-tab-live.mjs:1312` (`BROKEN_INSTRUMENT_MARKER`), `:1739-1750`
(the filter), `:787`, `:872`, `:1425`, `:1436`, `:1464` (the five emitters), `:1290-1296`
(the header claim), `:1563-1614` (`expectTableFaults` and its three fixtures, for contrast)

**Issue:** Commit `8c3a289` closed pass-2 WR-03 by filtering scored messages on
`f.includes(BROKEN_INSTRUMENT_MARKER)`. Two things about that closure are weaker than the
sibling guard plan 07 shipped for the case table:

1. **No re-runnable fixture.** `expectTableFaults` carries three literal fixtures
   (`EXPECT_TABLE_FIXTURES`) proving it rejects a duplicate, rejects a bare word, and accepts a
   well-formed table. The marker filter has none. Nothing demonstrates that a failures list
   containing only `align: ... (broken instrument, never a clean pass)` scores zero for
   `expect: 'align:'`, or that the new `named.length && !scored.length` branch fires and names
   the guard. A regression in the filter (e.g. `!f.includes` accidentally inverted, or the marker
   constant edited) leaves the self-test's PASS line unchanged. CLAUDE.md's Verification rule for
   a new check is a self-test that plants faults and requires each to go red; the scorer change
   is the one piece of new pass-3 logic in this file that has neither.

2. **Marker by literal, not by derivation.** The constant is defined at `:1312`, but the five
   emitters spell the string out by hand. `:787` and `:872` sit inside the `phaseExpression`
   template that is serialised into the page realm, so they cannot reference the Node-side
   constant directly — but `:1425`, `:1436` and `:1464` are in `assertReport`, the same realm,
   and still spell it. Rewording one of the five (e.g. "never a clean pass" → "not a clean pass")
   silently returns that message to scoreable status, and the header sentence at `:1292-1294`
   ("end with BROKEN_INSTRUMENT_MARKER") becomes false with nothing going red. The
   `deferred-items.md` entry that says "look for the message `named '...' only through
   broken-instrument reports`" in the next live run is a prediction about a filter that has never
   been shown to fire.

**Fix:** Build the three `assertReport` messages from the constant; pass it into the page realm
through `cfg` (which already carries every other derived string) and have `:787` and `:872`
concatenate `cfg.brokenInstrumentMarker`; and add a scorer fixture table beside
`EXPECT_TABLE_FIXTURES`, exercised in the same pre-flight:

```js
const SCORER_FIXTURES = [
    { what: 'a marker-only family scores nothing', failures: [`align: no pair (${BROKEN_INSTRUMENT_MARKER})`], expect: 'align:', scored: 0, named: 1 },
    { what: 'a contract message scores', failures: ['align: overlay off by 3px'], expect: 'align:', scored: 1, named: 1 },
    { what: 'another family does not score', failures: ['walk: not attached'], expect: 'align:', scored: 0, named: 0 },
];
```

with `scoreCase(failures, expect)` extracted from the loop so the fixture and the real path run
the same function. Optionally add a static assertion in `derive()` that every message in the
file whose prefix is a scoring family and whose text contains "broken instrument" also contains
the marker — derived from the file, compared as a set, red on either drift.
