## Long-run protocol

A command marked LONG (a full verify run, or a re-run of a row that launches a browser) can take
longer than the 10-minute foreground limit. Run each one this way, one at a time:

1. `mkdir -p .planning/phases/18-firefox-153-5-0esr/logs`, then confirm
   `git check-ignore -q .planning/phases/18-firefox-153-5-0esr/logs/{name}.log` exits 0.
   `.gitignore` ignores `*.log`, so logs are never committed.
2. `pgrep -af '[m]ach (build|clobber|package)|[v]erify-platform\.sh|[r]ebase-upstream\.sh|[p]ackage-linux\.sh'`
   prints nothing. Never start two long runs at once.
3. Snapshot `git status --porcelain` so you can compare it afterwards.
4. Launch it as one Bash call with `run_in_background` set:

```bash
L=.planning/phases/18-firefox-153-5-0esr/logs/{name}.log
{ s=$(date +%s); {command}; rc=$?; echo "PHASE18_WALL_SECONDS=$(( $(date +%s) - s ))"; echo "PHASE18_EXIT=$rc"; } > "$L" 2>&1
```

5. Wait for the completion notice. If the session was interrupted, wait on the sentinel with a
   Monitor until-loop (`until grep -q '^PHASE18_EXIT=' "$L"; do sleep 60; done`), never with a
   fixed sleep. Start no other long run in the meantime.
6. Read the result. `tail -n 2 "$L"` gives the wall seconds and the exit code; `tail -n 60 "$L"`
   gives the reason. If the process has exited and the log has no `PHASE18_EXIT=` line, the run
   was killed. Treat that as a failure, never as a pass.
